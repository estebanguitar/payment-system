# ADR 0002: 이벤트 기반 트랜잭션 분리 시 Kafka 미도입 사유 및 Spring Event (@TransactionalEventListener AFTER_COMMIT) 채택 배경

- **상태**: 승인됨 (Accepted)
- **날짜**: 2026-08-08
- **작성자**: Lead System Architect / Tech Lead

---

## 1. 맥락 및 문제 제기 (Context & Problem Statement)

결제 요청 수신 시 원장을 `PENDING` 상태로 저장한 후, 외부 PG 승인 요청 및 지갑 잔액 차감 로직을 수행해야 한다.
이 과정에서 외부 PG 연동(HTTP 통신) 중 지연이나 타임아웃이 발생할 때 `PENDING` 저장 트랜잭션의 DB Connection이 점유되는 현상을 막기 위해 **트랜잭션 경계 분리 및 이벤트 기반 아키텍처** 도입이 필요하다.

이때 메시지 브로커로 **Apache Kafka**를 도입할 것인지, 아니면 **Spring ApplicationEventPublisher + `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`** 구조를 채택할 것인지에 대한 트레이드오프 검토가 요구된다.

---

## 2. 기술 비교 및 분석 (Technology Trade-off Analysis)

| 비교 항목 | Apache Kafka 기반 이벤트 처리 | Spring Event (`@TransactionalEventListener AFTER_COMMIT`) |
| --- | --- | --- |
| **적합한 아키텍처** | 분산 마이크로서비스(MSA), 멀티 데이터베이스, 대규모 비동기 이벤트 스트리밍 | 모놀리식/단일 백엔드 애플리케이션, 인메모리/단일 RDB 환경 |
| **트랜잭션 분리** | Outbox 패턴/Debezium/CDC 추가 구성 필요 (Dual Write 문제 방지) | Spring 트랜잭션 시냅스 연동으로 `AFTER_COMMIT` 시점에 자동 보장 |
| **운영 및 인프라 복잡도** | 매우 높음 (Kafka Cluster, ZooKeeper/KRaft, Topic/Partition, DLQ 관리 필요) | 매우 낮음 (Spring Framework 내장 기능, 추가 인프라 0) |
| **테스트 용이성** | EmbeddedKafka 또는 Testcontainers 필요, CI/CD 빌드 시간 증가 | H2 인메모리 환경에서 외부 브로커 없이 빠르게 단위/통합 테스트 가능 |
| **현재 프로젝트 핏** | **Over-engineering (오버엔지니어링)** | **현재 요구사항 및 1페이즈 스코프에 최적으로 부합** |

---

## 3. 의사결정 (Decisions)

### 3.1 Apache Kafka를 선택하지 않은 이유
1. **단일 서비스 스코프 및 인프라 복잡도 관리**:
   - 본 프로젝트 1페이즈는 단일 Spring Boot 백엔드 애플리케이션과 인메모리 H2 DB를 기반으로 작동한다.
   - Kafka 도입 시 브로커 클러스터 운영 관리, 메시지 순서 보장, 파티셔닝 전략, 멱등 소비(Idempotent Consumer) 및 DLQ(Dead Letter Queue) 구축 등 **요구사항 범위를 크게 초과하는 과도한 인프라 복잡성(Over-engineering)**이 발생한다.
2. **이중 쓰기 문제(Dual Write Problem)**:
   - DB에 `PENDING` 저장과 Kafka 메시지 발행을 하나의 아토믹 작업으로 묶으려면 Transactional Outbox Pattern 및 CDC(Debezium) 같은 복잡한 패턴을 추가로 구현해야 하므로 1페이즈 개발 및 검증 생산성이 저하된다.

### 3.2 Spring Event (`@TransactionalEventListener`)를 선택한 이유
1. **완벽한 트랜잭션 경계 분리 (`TransactionPhase.AFTER_COMMIT`)**:
   - `PENDING` 원장 생성 트랜잭션이 성공적으로 **DB에 Commit된 직후**에만 이벤트를 발행/수신한다.
   - 원장 저장 실패 시 외부 PG 호출 이벤트 자체가 발송되지 않아 데이터 불일치를 원천 차단한다.
   - 외부 PG HTTP 연동 시에는 `PENDING` 트랜잭션이 이미 Commit되고 DB 커넥션이 반납된 상태이므로 **DB Connection Pool 고사(Exhaustion) 위험이 100% 제거**된다.
2. **모놀리식 내에서의 높은 디커플링 (Decoupling)**:
   - `PaymentService`(결제 원장 도메인)와 `PgClient`/`WalletService`(외부 연동 및 잔액 차감 도메인) 간의 직접적인 강결합 의존성을 제거한다.
3. **가볍고 신속한 자동화 테스트**:
   - 별도의 외부 브로커 모킹 없이 Spring Boot Test environment 및 H2 DB 상에서 결정론적인 인수 테스트 작성이 가능하다.

## 4. 이벤트 기반 처리 흐름도

```
[Client] ──> (1) POST /payments 
                │
                v
[PaymentService] ──> (2) @Transactional 시작 ──> Payment PENDING 저장
                │
                ├──> (3) DB Commit 성공! (DB 커넥션 반납)
                │
                v
[Event Publisher] ──> (4) PaymentCreatedEvent 발행
                │
                v
[PaymentEventListener] (@TransactionalEventListener phase = AFTER_COMMIT)
                │
                ├──> (5) 외부 PG 승인 요청 (DB 커넥션 없는 상태에서 HTTP 연동)
                │
                └──> (6) 승인 결과 수신 후 별도 @Transactional 로 잔액 차감 & 상태 갱신
```

---

## 5. 결과 및 기대 효과 (Consequences)

* **안전성 확보**: 외부 PG 장애/지연 시에도 DB 커넥션이 고갈되지 않아 결제 시스템 전반의 고가용성 유지.
* **설계 깔끔함**: 별도 인프라(Kafka) 없이 Spring 내장 이벤트 엔진만으로 트랜잭션 격리 및 이벤트 기반 아키텍처 구현.
* **테스트 용이성**: JUnit 5 기반으로 동시성 및 비동기 이벤트 처리 테스트를 손쉽게 검증 가능.
