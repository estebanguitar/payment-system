## 2. 목표와 구현 원칙

- 결제, 취소, 지갑의 상태 전이와 금액 불변식을 엔티티 내부에 캡슐화한다.
- 엔티티에는 공개 Setter를 두지 않고 의도가 드러나는 도메인 메서드만 제공한다.
- 금액은 원화 1원 단위의 `long`으로 표현하며 모든 요청 금액은 양수여야 한다.
- JPA 엔티티는 영속성 매핑만 포함하고 Repository 및 트랜잭션 경계는 도메인 밖에 둔다.
- Aggregate 간 연결은 불필요한 객체 그래프와 지연 로딩 부작용을 피하기 위해 식별자 값으로 참조한다.
- 시간은 테스트 가능성을 위해 생성 팩터리에서 `LocalDateTime` 값을 명시적으로 받는다. 현재 스키마와 API 명세의 시각 타입에 맞추되, 운영 DB 전환 시 `Instant` 채택 여부를 재검토한다.
- Lombok은 `@Getter`, `@NoArgsConstructor(access = AccessLevel.PROTECTED)`만 엔티티에 적용하고 `@Data`, `@Setter`, 엔티티 `@Builder`·`@AllArgsConstructor`는 사용하지 않는다.

## 3. 패키지 및 파일 구성

기준 패키지는 `com.example.paymentsystem.domain`으로 한다.

```text
domain/
├─ customer/
│  └─ Customer.java
├─ wallet/
│  ├─ Wallet.java
│  ├─ WalletTransaction.java
│  └─ WalletTransactionType.java
├─ payment/
│  ├─ Payment.java
│  ├─ PaymentStatus.java
│  └─ PaymentFailureReason.java
├─ cancel/
│  ├─ PaymentCancel.java
│  ├─ CancelType.java
│  └─ CancelStatus.java
├─ pg/
│  └─ PgResponseLog.java
├─ outbox/
│  ├─ PaymentOutbox.java
│  ├─ OutboxEventType.java
│  └─ OutboxStatus.java
└─ exception/
   ├─ DomainErrorCode.java
   ├─ DomainException.java
   ├─ InvalidAmountException.java
   ├─ InsufficientBalanceException.java
   ├─ InvalidPaymentStateException.java
   └─ InvalidCancelAmountException.java
```

도메인 예외는 HTTP 상태를 알지 않으며 `DomainErrorCode`에 정의된 업무 오류 코드와 표준 메시지를 재사용한다. Presentation 계층의 HTTP 매핑은 후속 구현 범위로 남긴다.

## 4. Aggregate 경계와 책임

| Aggregate | Root | 내부 책임 | 외부에서 보장할 사항 |
| --- | --- | --- | --- |
| Customer | `Customer` | 고객 식별자와 기본 정보 생성 | 고객 중복 여부 및 조회 |
| Wallet | `Wallet` | 잔액 증가·차감, 음수 잔액 방지 | 비관적 잠금, 거래 이력 동시 저장 |
| Payment | `Payment` | 결제 상태 전이, 실패 사유, 누적 취소 금액 | 멱등성 조회, 결제 단위 잠금, 트랜잭션 |
| PaymentCancel | `PaymentCancel` | 취소 시도 상태와 실패 이력 | 원 결제와의 원자적 반영, 외부 PG 결과 조정 |
| 지원 원장 | 각 엔티티 | 거래·PG 응답·아웃박스 이력의 불변 데이터 보관 | 저장 및 조회, 암호화·재시도 처리 |

`WalletTransaction`, `PgResponseLog`, `PaymentOutbox`는 기존 물리 스키마에 독립 ID가 있으나, 업무상 수정 가능한 Aggregate로 취급하지 않는다. 생성 후 허용된 상태 변경만 제공하는 이력 모델로 구현한다.

## 5. 엔티티별 코드 수준 설계

### 5.1 Customer

- `@Entity`, `@Table(name = "customer")`와 컬럼 길이·null 조건을 V1 Flyway 스키마와 일치시킨다.
- 필드: `id`, `customerId`, `name`, `email`, `createdAt`, `updatedAt`.
- `static Customer create(String customerId, String name, String email, LocalDateTime now)` 팩터리를 제공한다.
- 식별자·이름의 공백/누락을 거절하고 이메일 형식 검증은 API 입력 계층 책임으로 둔다.

### 5.2 Wallet

- 필드: `id`, `customerId`, `balance`, `createdAt`, `updatedAt`.
- `static Wallet create(String customerId, LocalDateTime now)`는 초기 잔액을 0으로 고정한다.
- `increase(long amount, LocalDateTime now)`는 양수 검증 후 `Math.addExact`로 overflow를 차단한다.
- `decrease(long amount, LocalDateTime now)`는 양수와 잔액 충분 여부를 확인한 뒤 차감한다.
- 각 변경 메서드는 변경 후 잔액을 반환하여 Application 계층이 같은 트랜잭션에서 `WalletTransaction`을 생성할 수 있게 한다.
- 잠금 어노테이션은 Repository에 적용하며 엔티티에는 동시성 인프라 코드를 넣지 않는다.

### 5.3 WalletTransaction

- 필드: `id`, `walletId`, `transactionType`, `amount`, `balanceAfter`, `paymentId`, `cancelId`, `idempotencyKey`, `createdAt`.
- 타입별 정적 팩터리를 둔다.
  - `topUp(walletId, amount, balanceAfter, idempotencyKey, now)`
  - `payment(walletId, amount, balanceAfter, paymentId, now)`
  - `refund(walletId, amount, balanceAfter, paymentId, cancelId, now)`
- 참조 규칙을 팩터리에서 검증한다: 충전은 결제·취소 ID 없음, 결제 차감은 결제 ID 필수, 환불은 결제·취소 ID 필수.
- 모든 이력 금액은 양수이며 `balanceAfter`는 0 이상이어야 한다.

### 5.4 Payment

- 필드: `id`, `idempotencyKey`, `customerId`, `amount`, `status`, `failureReason`, `accumulatedCancelAmount`, `createdAt`, `updatedAt`.
- `createPending(...)`는 양수 금액, 필수 멱등키·고객 ID를 검증하고 `PENDING`, 누적 취소액 0으로 생성한다.
- 허용 상태 전이를 아래 메서드로 제한한다.
  - `complete(now)`: `PENDING -> COMPLETED`
  - `fail(PaymentFailureReason reason, now)`: `PENDING -> FAILED`; 사유 필수
  - `applyCancellation(long amount, now)`: `COMPLETED` 또는 `PARTIALLY_CANCELED`에서만 실행하고 누적액을 증가시킨 뒤 잔액에 따라 `PARTIALLY_CANCELED` 또는 `CANCELED`로 전환
- 조회 메서드: `remainingCancelableAmount()`, `isCancelable()`, `matchesRequest(customerId, amount)`.
- 완료·취소 상태에서는 `failureReason == null`, 실패 상태에서는 사유가 필수라는 불변식을 유지한다.
- 누적 취소액은 0 이상 원 결제 금액 이하여야 하며 덧셈에는 `Math.addExact`를 사용한다.

### 5.5 PaymentCancel

- 필드: `id`, `paymentId`, `idempotencyKey`, `cancelType`, `amount`, `status`, `failureReason`, `pgCancelTransactionId`, `createdAt`, `completedAt`.
- `createPending(paymentId, idempotencyKey, cancelType, requestedAmount, remainingAmount, now)`에서 취소 유형과 금액을 검증한다.
  - `FULL`: 요청 금액은 남은 취소 가능 금액과 같아야 한다.
  - `PARTIAL`: 0보다 크고 남은 취소 가능 금액보다 작아야 한다.
- `complete(pgCancelTransactionId, now)`: `PENDING -> COMPLETED`.
- `fail(PaymentFailureReason reason, now)`: `PENDING -> FAILED`; 원 결제 상태는 변경하지 않는다.
- 취소 실패 사유는 현재 스키마와 요구사항에 별도 enum이 정의되지 않았으므로 1차 구현에서는 `PaymentFailureReason`을 재사용한다. PG 취소 고유 사유가 추가되면 별도 `CancelFailureReason`으로 분리한다.

### 5.6 PgResponseLog

- 필드: `id`, `paymentId`, `pgTransactionId`, `pgResponseCode`, `encryptedPayload`, `receivedAt`.
- `create(...)` 팩터리는 암호화가 완료된 payload만 받으며 빈 payload를 거절한다.
- 암호화·복호화 책임과 평문 보관은 Infrastructure 계층에 둔다.
- 엔티티 `toString`을 만들지 않아 암호문 및 메타데이터의 우발적 로그 노출을 줄인다.

### 5.7 PaymentOutbox

- 필드: `id`, `paymentId`, `idempotencyKey`, `eventType`, `payload`, `status`, `retryCount`, `createdAt`, `updatedAt`.
- `createPaymentRequested(...)`는 `INIT`, 재시도 0으로 생성한다.
- `markPublished(now)`: `INIT -> PUBLISHED`만 허용한다.
- `recordFailure(now)`: `INIT` 상태에서 재시도 횟수를 증가시키며 overflow를 차단한다.
- `markFailed(now)`는 후속 재시도 정책이 정한 한도에 도달했을 때 Application/Infrastructure 계층이 호출한다.
- payload 직렬화와 폴링 기준 시각 계산은 도메인 밖에 둔다.

## 6. 열거형 정의

| 열거형 | 값 |
| --- | --- |
| `WalletTransactionType` | `TOP_UP`, `PAYMENT`, `REFUND` |
| `PaymentStatus` | `PENDING`, `COMPLETED`, `PARTIALLY_CANCELED`, `CANCELED`, `FAILED` |
| `PaymentFailureReason` | `INSUFFICIENT_BALANCE`, `SYSTEM_ERROR`, `EXTERNAL_PAYMENT_REJECTED` |
| `CancelType` | `FULL`, `PARTIAL` |
| `CancelStatus` | `PENDING`, `COMPLETED`, `FAILED` |
| `OutboxEventType` | `PAYMENT_REQUESTED` |
| `OutboxStatus` | `INIT`, `PUBLISHED`, `FAILED` |

모든 enum은 `EnumType.STRING`으로 매핑하여 DDL의 `VARCHAR` 및 운영 가독성과 일치시킨다.

- 지갑 생성 시 잔액 0, 정상 충전·차감, 0/음수 금액 거절, 부족 잔액 거절, overflow 거절.

## 9. 선행 결정 및 후속 계층 요구사항

### 9.1 구현 전 확정이 필요한 사항

1. **글로벌 멱등키 제약 불일치**: 요구사항은 결제·취소·충전을 포함한 시스템 전체 유일성을 요구하지만 현재 V1 스키마는 각 테이블 안에서만 UNIQUE이다. 도메인 레이어만으로 원자적 글로벌 유일성을 보장할 수 없으므로, 별도 `idempotency_record` 테이블 도입 또는 “업무 유형별 유일”로 요구사항 변경 중 하나를 승인해야 한다.
2. **취소 동시성 제어**: 동일 결제에 대한 동시 부분 취소가 누적 금액을 초과하지 않도록 후속 Repository에 `Payment` 비관적 쓰기 잠금을 추가해야 한다. 이는 기존 지갑 잠금 전략의 적용 범위를 원 결제 Aggregate까지 확장하는 결정이다.
3. **취소 실패 사유 모델**: 현재 요구사항은 취소 실패 기록만 요구하고 구체 enum은 정의하지 않았다. 1차 구현의 `PaymentFailureReason` 재사용 여부를 승인받고, 외부 취소 거절을 별도로 구분할 필요가 있으면 enum과 API 명세를 보완한다.

### 9.2 후속 구현에 전달할 제약

- 지갑 변경과 `WalletTransaction` 저장은 같은 트랜잭션에서 수행한다.
- 결제 완료 시 지갑 잠금·차감·거래 이력·결제 상태 변경을 하나의 트랜잭션으로 묶는다.
- 취소 완료 시 원 결제 잠금·지갑 잠금·환불 거래·취소 완료·누적 취소액 변경을 하나의 트랜잭션으로 묶는다.
- `PENDING Payment`와 `INIT PaymentOutbox`는 같은 트랜잭션으로 생성한다.
- 데이터베이스 유일성 위반은 후속 Application 계층에서 멱등 재조회 또는 충돌 응답으로 해석한다.

| 구현 영역 | 요구사항 ID |
