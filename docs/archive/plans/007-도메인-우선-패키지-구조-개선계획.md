## 2. 배경과 문제 정의

현재 코드는 `domain`, `application`, `infrastructure`, `presentation`을 최상위로 두고 그 아래에 업무 패키지를 배치한다. 계층 책임을 찾기는 쉽지만 하나의 업무 기능을 수정할 때 여러 최상위 패키지를 오가야 하고, 특정 도메인을 모듈 또는 서비스로 분리할 때 포함 파일과 의존 관계를 한눈에 확인하기 어렵다.

이번 작업은 공개 API, 데이터베이스 스키마 및 업무 동작을 변경하지 않는 구조 리팩터링이다. 최상위 업무 경계를 먼저 표현하고 각 경계 내부에서 `domain`, `application`, `infrastructure`, `presentation`을 구분한다.

## 3. 목표

- 결제, 지갑, 고객, 취소, 아웃박스, 감사 로그의 코드와 테스트를 업무 경계별로 응집한다.
- 도메인 내부 의존 방향을 `presentation → application → domain`으로 명확히 한다.
- Infrastructure가 Domain/Application 계약을 구현하도록 하며 역방향 의존을 금지한다.
- 도메인 간 직접 참조를 최소화하고 허용된 Application 계약으로만 협력하도록 한다.
- 향후 Gradle 멀티모듈 또는 MSA 분리 시 이동할 코드 범위를 명확히 한다.
- 기존 REST 경로, JSON 계약, 오류 코드, Flyway 이력 및 JPA 테이블을 유지한다.
- ArchUnit 테스트로 패키지 경계를 자동 검증한다.

## 4. 제외 범위

- 공개 REST API 경로와 요청·응답 필드 변경
- 데이터베이스 테이블·컬럼·인덱스 및 Flyway migration 변경
- 결제·지갑 간 단일 DB 트랜잭션을 분산 트랜잭션으로 변경
- Gradle 멀티모듈의 실제 분리
- `outbox-worker`의 독립 Gradle 모듈·프로세스·배포 구현
- 잔고 및 PG 원장 대사 기능 구현
- 결제·지갑·감사 기능의 MSA 전환
- 비동기 메시지 브로커 도입
- 업무 로직, 예외 정책 및 동시성 전략 변경
- 패키지 이동과 무관한 기능 추가 또는 성능 최적화

## 6. 도메인 경계 정의

### 6.1 Customer

- 고객 식별과 고객 존재 조회를 소유한다.
- 고객이 지갑·결제 엔티티를 직접 소유하거나 조작하지 않는다.
- 다른 도메인은 고객 엔티티 대신 고객 식별자 또는 Application 조회 계약을 사용한다.

### 6.2 Wallet

- 지갑, 잔액 불변식, 지갑 거래 이력과 충전 유스케이스를 소유한다.
- 결제 차감과 취소 환불은 Wallet Application 계약을 통해 호출한다.
- Payment Entity 또는 Cancellation Entity를 직접 참조하지 않고 식별자만 저장한다.

### 6.3 Payment

- 결제 원장, 상태 전이, 결제 생성·처리·결과 조회를 소유한다.
- 고객 확인, 지갑 차감 및 PG 승인은 각 도메인의 Application Port를 통해 협력한다.
- 취소 상세 구현을 직접 참조하지 않고 취소 조회 계약 또는 결과 DTO를 사용한다.

### 6.4 Cancellation

- 전액·부분 취소, 누적 취소 금액 검증과 취소 결과를 소유한다.
- 원 결제 상태 전이와 지갑 환불은 명시적인 Application 계약을 통해 수행한다.
- 외부 PG 취소 Port는 Cancellation Application에서 선언한다.

### 6.5 Outbox

- 결제·취소 후속 처리 이벤트, 재시도 상태와 고립 이벤트 복구를 소유한다.
- 이벤트 payload는 발행 도메인의 공개 Application DTO 또는 버전이 있는 이벤트 계약을 사용한다.
- 도메인 엔티티 전체를 payload로 직렬화하지 않는다.
- 이번 단계에서는 `outbox`를 최상위 도메인 패키지로 응집하는 데 집중하고 실행 모듈은 분리하지 않는다.
- 패키지 구조 개선 완료 후 별도 구현계획과 ADR을 통해 `outbox-worker` Gradle 모듈 및 독립 배포 프로세스로 분리한다.
- Worker 분리 전까지 API와 Scheduler의 기존 실행 동작, 트랜잭션 및 재시도 정책을 변경하지 않는다.

### 6.6 Audit

- HTTP 요청 감사 정보, 추적 ID, 저장·검색 계약을 소유한다.
- 다른 업무 도메인 엔티티를 참조하지 않는다.
- 삭제 API, 자동 삭제 및 보존 만료 삭제 기능은 사용자 결정에 따라 포함하지 않는다.

### 6.7 Idempotency

- 전역 멱등키 등록과 요청 fingerprint 충돌 판정을 소유한다.
- 결제·충전·취소는 공통 멱등 Application 계약을 호출한다.
- 요청 유형 enum은 멱등 경계에서 유지한다.

### 6.8 PG

- 외부 PG 승인·취소 Port, 결과 계약, Fake Adapter와 응답 로그 암호화 연계를 소유한다.
- PG는 내부 Payment Entity를 직접 참조하지 않고 command/result만 사용한다.
- 실제 PG사별 Adapter 추가 시 `pg.infrastructure.<provider>`로 확장한다.

## 7. 의존성 규칙

### 7.1 도메인 내부 계층 규칙

- `*.domain`은 Spring Service, Repository, Controller 및 다른 계층에 의존하지 않는다.
- `*.application`은 같은 도메인의 `domain`, 허용된 외부 Application Port 및 `shared.application`만 의존한다.
- `*.infrastructure`는 같은 도메인의 Domain/Application 계약을 구현할 수 있다.
- `*.presentation`은 같은 도메인의 Application Service/DTO와 `shared.presentation`만 의존한다.
- Controller가 Repository와 Entity를 직접 참조하지 않는다.

### 7.2 도메인 간 규칙

- 다른 도메인의 `infrastructure` 또는 `presentation` 패키지 참조를 금지한다.
- 다른 도메인의 Domain Entity 직접 참조를 원칙적으로 금지한다.
- 도메인 간 호출은 대상 도메인의 Application Port 또는 공개 DTO로 제한한다.
- 순환 의존이 발생하면 orchestration 책임을 가진 Application Service 또는 명시적인 Port를 도입한다.
- `shared`는 순환 의존을 숨기는 우회 경로로 사용하지 않는다.

### 7.3 예외 허용 절차

불가피한 예외는 ArchUnit ignore로 바로 추가하지 않는다. 의존 이유, 대안, 제거 계획을 ADR에 기록하고 사용자 승인을 받은 뒤 한시적으로 허용한다.

## 8. 파일 이동 계획

### 8.1 Customer

| 현재 | 목표 |
| --- | --- |
| `domain/entity/customer/Customer` | `customer/domain/Customer` |
| `application/service/customer/CustomerQueryService` | `customer/application/CustomerQueryService` |
| `infrastructure/repository/customer/CustomerRepository` | `customer/infrastructure/CustomerRepository` |

### 8.2 Wallet

| 현재 영역 | 목표 영역 |
| --- | --- |
| 지갑·지갑 거래 Entity/enum | `wallet/domain` |
| `WalletCommand`, `WalletResult` | `wallet/application/dto` |
| 지갑 Service | `wallet/application` |
| 지갑 Repository | `wallet/infrastructure` |
| 지갑 Controller/DTO | `wallet/presentation`, `wallet/presentation/dto` |

### 8.3 Payment

| 현재 영역 | 목표 영역 |
| --- | --- |
| 결제 Entity/status/failure reason | `payment/domain` |
| Payment command/result/event | `payment/application/dto`, `payment/application/event` |
| 생성·처리·결과·Facade·조회 Service | `payment/application` |
| Payment Repository/Specification | `payment/infrastructure` |
| Payment 및 고객·운영 조회 Controller/DTO | `payment/presentation`, `payment/presentation/dto` |

고객 결제 조회와 운영 결제 조회는 Payment가 결제 검색의 주체이므로 Payment 경계에 둔다. 향후 별도 Query 모듈이 필요해질 때 CQRS ADR로 분리한다.

### 8.4 Cancellation

| 현재 영역 | 목표 영역 |
| --- | --- |
| 취소 Entity/status/type | `cancellation/domain` |
| 취소 command/result/event/view | `cancellation/application/dto`, `cancellation/application/event` |
| 취소 생성·처리·결과·Facade | `cancellation/application` |
| 취소 Repository | `cancellation/infrastructure` |
| 취소 HTTP 요청/응답 DTO | `cancellation/presentation/dto` 또는 Payment Controller 경계의 조립 DTO |

취소 URL이 `/payments/{paymentId}/cancel`인 사실은 코드 소유권과 별개다. HTTP Controller는 Payment Presentation에 유지할 수 있으나 취소 명령과 결과는 Cancellation Application 계약만 사용한다.

### 8.5 Outbox, Audit, Idempotency, PG

- 각각 최상위 `outbox`, `audit`, `idempotency`, `pg` 경계로 이동한다.
- Repository, Properties, Scheduler, Filter 및 Adapter도 소유 도메인 내부 계층으로 이동한다.
- 감사 Filter와 전역 API 오류 처리의 연결은 `shared.presentation`의 안전한 오류 문맥 계약으로 분리한다.
- PG 응답 로그 Entity/Repository는 `pg` 경계가 소유한다.

### 8.6 Shared

다음 후보만 검토한다.

- `shared.application`: 범용 `PageResult`
- `shared.presentation`: `ApiResponse`, `ErrorDetail`, `GlobalExceptionHandler`, OpenAPI 공통 설정
- `shared.infrastructure`: 전역 Spring configuration 중 특정 도메인이 소유하지 않는 항목
- 공통 오류 코드라도 업무 오류는 각 도메인에 유지하고 HTTP 매핑만 shared에서 조합한다.

## 9. 오류 코드 재배치

현재 단일 `DomainErrorCode`, `ApplicationErrorCode`는 도메인 경계를 흐릴 수 있다. 다만 이번 작업에서 오류 문자열과 HTTP 계약을 변경해서는 안 된다.

1. 1단계에서는 enum 값과 문자열을 유지한 채 `shared`에 둔다.
2. 각 도메인의 소비 위치와 소유권을 정리한다.
3. 도메인별 enum 분리는 별도 리팩터링 계획과 호환성 테스트를 거쳐 수행한다.

이번 패키지 이동과 동시에 오류 코드를 분할하지 않아 변경 축을 하나로 제한한다.

## 10. 데이터와 트랜잭션 영향

- `@Entity`, `@Table`, `@Column` 및 연관관계 매핑은 변경하지 않는다.
- Flyway V1~V4 파일과 checksum을 변경하지 않는다.
- Repository query method, Specification 조건 및 비관적 잠금 설정을 유지한다.
- `@Transactional`, propagation, readOnly 속성과 외부 PG 호출 경계를 유지한다.
- Spring Data Repository 탐색과 Entity scan이 새 루트에서 정상 동작하는지 통합 테스트로 검증한다.
- package 이동으로 직렬화된 클래스명이 저장 데이터에 포함되는 항목이 있는지 확인한다. 현재 Outbox JSON은 명시 DTO 필드 기반을 유지해야 한다.

## 11. Presentation 및 API 호환성

- 모든 `/api/v1` 경로, HTTP 메서드와 상태 코드를 유지한다.
- `ApiResponse`의 `code`, `message`, `returnObject` 구조를 유지한다.
- Swagger path, schema 필드 및 필수 Header 계약을 이동 전후 비교한다.
- Jackson JSON property는 Java package와 무관해야 하며 snapshot 또는 JSONPath 테스트로 확인한다.
- 추적 ID와 감사 Filter 순서를 유지한다.
- 운영 감사 로그 API에는 삭제 endpoint를 추가하지 않는다.

## 12. 테스트 패키지 재설계

Production 패키지와 동일한 도메인 우선 구조로 테스트를 이동한다.

```text
src/test/java/com/example/paymentsystem
├─ customer
├─ wallet
├─ payment
├─ cancellation
├─ outbox
├─ audit
├─ idempotency
├─ pg
├─ shared
└─ architecture
```

- 단위 테스트는 대상 클래스와 동일한 도메인·계층 패키지에 둔다.
- 여러 도메인을 조합하는 통합 테스트는 orchestration 주체 도메인 또는 `architecture/integration`에 둔다.
- 테스트 package 직접 접근도 import로 교체하고 static import는 기존 테스트를 무리하게 일괄 변경하지 않되 신규·수정 코드에서는 지양한다.

## 13. ArchUnit 검증 계획

`build.gradle`에 ArchUnit JUnit 5 의존성을 추가하고 다음 테스트를 생성한다.

- `architecture/DomainLayerDependencyTest`
  - 모든 `..domain..`이 application, infrastructure, presentation에 의존하지 않는지 검증
- `architecture/ApplicationLayerDependencyTest`
  - Application이 Presentation과 Infrastructure에 의존하지 않는지 검증
- `architecture/DomainBoundaryDependencyTest`
  - 다른 도메인의 Infrastructure/Presentation 참조 금지
  - 허용된 Application Port 외 직접 도메인 참조 탐지
- `architecture/PresentationDependencyTest`
  - Controller가 Repository와 Entity를 직접 참조하지 않는지 검증
- `architecture/NamingConventionTest`
  - Controller, Service, Repository 및 DTO의 패키지 위치 규칙 검증

초기 테스트는 현재 의존 위반을 목록화하는 탐색 단계로 실행한다. 목표 구조 이관 완료 시 예외 없는 강제 규칙으로 전환한다.

## 14. 단계별 구현계획

### 14.1 0단계: 기준선 고정

1. PR #5 병합 후 최신 `main`에서 브랜치를 생성한다.
2. 이 문서를 새 브랜치 최초 커밋으로 생성한다.
3. 전체 테스트, JaCoCo 및 `/v3/api-docs` 결과를 기준선으로 저장한다.
4. 현재 package 간 의존 그래프와 순환 의존을 분석한다.

### 14.2 1단계: Shared와 독립 경계 이동

1. `shared.presentation` 공통 응답·예외·OpenAPI 설정을 이동한다.
2. 외부 업무 의존이 적은 Audit 경계를 이동한다.
3. Customer와 PG 경계를 이동한다.
4. 각 묶음 이동 후 compile과 해당 테스트를 실행한다.

### 14.3 2단계: Wallet과 Idempotency 이동

1. Wallet Domain, Application, Infrastructure, Presentation을 한 묶음으로 이동한다.
2. Idempotency 경계를 이동하고 결제·충전·취소의 참조를 Port로 정리한다.
3. 지갑 비관적 잠금과 멱등 충돌 테스트를 실행한다.

### 14.4 3단계: Payment와 Cancellation 이동

1. Payment Entity·Application·Repository·Presentation을 이동한다.
2. Cancellation을 독립 경계로 이동한다.
3. Payment Controller가 Cancellation Application 계약만 사용하도록 조정한다.
4. 고객·운영 조회 조립 책임을 Payment Application에 유지한다.
5. 결제·취소 트랜잭션 및 PG 실패 회귀 테스트를 실행한다.

### 14.5 4단계: Outbox 이동과 순환 제거

1. Outbox Domain·Application·Infrastructure를 이동한다.
2. Payment/Cancellation 이벤트 계약의 위치와 의존 방향을 정리한다.
3. 고립 이벤트 복구 및 retry 테스트를 실행한다.
4. 잔여 순환 의존과 구 패키지 참조를 제거한다.
5. Scheduler와 후속 처리 서비스를 `outbox` 경계에 응집하되 이번 단계에서는 물리 모듈을 분리하지 않는다.

### 14.6 5단계: 테스트 이동과 아키텍처 규칙 강제

1. 테스트를 도메인 우선 구조로 이동한다.
2. ArchUnit 의존 규칙을 추가한다.
3. `rg`로 구 패키지 경로와 코드 본문의 fully qualified type 참조가 0건인지 확인한다.
4. 빈 구 패키지 디렉터리를 제거한다.

### 14.7 6단계: 전체 검증 및 문서 현행화

1. `clean test jacocoTestReport bootJar`를 실행한다.
2. OpenAPI path/schema를 기준선과 비교한다.
3. Docker image build와 Compose 기동을 검증한다.
4. Flyway V1~V4 적용과 데이터 접근을 검증한다.
5. 요구사항, 아키텍처, API 명세, ADR 및 대화 기록을 실제 구조와 일치시킨다.

## 15. 커밋 전략

1. `docs: 도메인 우선 패키지 개선계획 추가` — 새 브랜치 최초 커밋
2. `refactor: shared 및 audit 패키지 이관`

4. `refactor: wallet 및 idempotency 패키지 이관`
5. `refactor: payment 및 cancellation 패키지 이관`

7. `test: 도메인 우선 테스트 구조 및 아키텍처 규칙 적용`

## 17. 완료 기준

- 최상위 업무 경계와 내부 계층 구조가 목표 패키지와 일치한다.
- 구 역할 우선 package import와 코드 본문의 fully qualified type 직접 참조가 0건이다.
- Domain이 Application, Infrastructure, Presentation에 의존하지 않는다.
- 도메인 간 Infrastructure/Presentation 직접 참조가 없다.
- Controller가 Repository와 Entity를 직접 참조하지 않는다.
- 기존 API 경로, JSON, 오류 코드와 HTTP 상태가 유지된다.
- Flyway V1~V4와 기존 테이블 매핑이 변경되지 않는다.
- 전체 단위·통합·HTTP·OpenAPI·ArchUnit 테스트가 통과한다.
- JaCoCo HTML 리포트와 bootJar가 생성된다.
- Docker Compose 기동 및 health 확인이 성공한다.
- 구조 변경과 잔여 트레이드오프가 아키텍처 문서와 ADR에 기록된다.

## 18. 승인 요청 사항

1. 최상위 경계를 customer, wallet, payment, cancellation, outbox, audit, idempotency, pg, shared로 구성
2. 각 도메인 내부에 domain, application, infrastructure, presentation 계층 유지
3. 고객·운영 결제 조회를 1단계에서는 Payment 경계가 소유
4. 공통 오류 enum 분리는 이번 작업에서 제외하고 후속 리팩터링으로 분리
5. ArchUnit으로 계층 및 도메인 간 의존 규칙 강제
6. 공개 API, DDL, Flyway 이력과 트랜잭션 전략은 변경하지 않음
7. PR #5 병합 전에는 본 계획을 어떤 커밋에도 포함하지 않음
8. 이번 작업은 패키지 이동만 수행하고 `outbox-worker` 모듈 분리와 잔고 대사는 후속 요구사항으로 이관

## 19. 구현 결과

- `customer`, `wallet`, `payment`, `cancellation`, `outbox`, `audit`, `idempotency`, `pg`, `shared` 최상위 업무 경계로 운영 코드를 이관했다.
- 각 업무 경계 내부에 실제 책임에 따라 Domain, Application, Infrastructure, Presentation 패키지를 유지했다.
