# 잔고 및 원장 대사 구현계획

> 상태: 중단됨. 잔고·원장 대사는 현재 MVP에서 제거하며, 운영상 필요성과 조치 권한이 별도로 승인되기 전에는 구현하지 않는다.

## 1. 문서 정보

| 항목 | 내용 |
| --- | --- |
| 문서 목적 | 내부 결제·지갑·취소 원장과 외부 PG·Outbox 처리 결과의 불일치를 탐지하고 안전하게 운영 조치·재검증하는 기능을 코드 수준으로 정의한다. |
| 작성 관점 | PM / Software Architect / Tech Lead |
| 작성일 | 2026-08-09 |
| 상태 | 승인 및 1단계 구현 완료 |
| 요구사항 | `REC-001`, `REC-002`, `REC-003` |
| 선행 조건 | 도메인 우선 패키지 구조 개선 및 `outbox-worker` 독립 실행 구조 완료 |
| 예정 브랜치 | `feature/ledger-reconciliation` |

## 2. 목표와 안전 원칙

- 온라인 결제 처리와 분리된 Batch/Worker에서 대사를 수행한다.
- 원장·PG·Outbox 데이터는 대사 시점의 스냅샷으로 읽고 검사 결과를 별도 원장에 저장한다.
- 같은 검사 범위의 반복 실행이 대사 결과를 중복 오염시키지 않도록 멱등성을 보장한다.
- 불일치 상태, 근거 값, 운영 판정, 조치 이력 및 재검증 결과를 추적한다.
- 1단계는 탐지·보고·수동 조치 기록만 제공하고 결제·지갑·취소 원장을 자동 수정하지 않는다.
- 대사 실패와 지연이 온라인 API 트랜잭션과 Outbox 후속 처리를 차단하지 않는다.

## 3. 구현 범위

### 3.1 포함 범위

- 기간·식별자 범위 기반 대사 실행
- 지갑 거래 합계와 현재 잔액 대사
- 결제·지갑 차감 거래 대사
- 취소·지갑 환불 거래 대사
- 누적 취소 금액과 완료 취소 합계 대사
- 결제·취소·Outbox 상태 조합 대사
- 장기 `PENDING` 및 장기 `INIT` 탐지
- PG 거래 식별자·응답 로그 존재 여부 확인
- 대사 실행·불일치 Case·운영 조치 이력 저장
- 운영 검색·단건·조치 등록·재검증 API
- 실행/불일치/해결/실패 메트릭과 health 정보

### 3.2 제외 범위

- 결제·지갑·취소 원장 자동 수정
- PG 자동 승인 취소 또는 자동 재승인
- 누락 거래의 자동 생성
- 감사 로그 삭제 또는 대사 결과 삭제 API
- 인증·인가 체계 자체 구현
- 외부 PG의 실제 정산 파일·금융망 연동
- 대사 결과를 근거로 한 자동 금전 보상

## 4. 대사 유형

`ReconciliationMismatchType` enum으로 다음 유형을 정의한다.

| 유형 | 판정 기준 | 기본 심각도 |
| --- | --- | --- |
| `WALLET_BALANCE_MISMATCH` | 지갑 현재 잔액과 거래 이력 기반 계산 잔액 불일치 | CRITICAL |
| `PAYMENT_DEBIT_MISSING` | 완료 결제에 대응하는 PAYMENT 지갑 거래 없음 | CRITICAL |
| `PAYMENT_DEBIT_AMOUNT_MISMATCH` | 결제 금액과 차감 거래 금액 불일치 | CRITICAL |
| `CANCEL_REFUND_MISSING` | 완료 취소에 대응하는 REFUND 지갑 거래 없음 | CRITICAL |
| `CANCEL_REFUND_AMOUNT_MISMATCH` | 취소 금액과 환불 거래 금액 불일치 | CRITICAL |
| `CANCEL_ACCUMULATION_MISMATCH` | 결제 누적 취소 금액과 완료 취소 합계 불일치 | CRITICAL |
| `CANCEL_AMOUNT_OVER_PAYMENT` | 완료 취소 합계가 원 결제 금액 초과 | CRITICAL |
| `PAYMENT_STUCK_PENDING` | 기준 시간보다 오래된 PENDING 결제 | HIGH |
| `CANCEL_STUCK_PENDING` | 기준 시간보다 오래된 PENDING 취소 | HIGH |
| `OUTBOX_STUCK_INIT` | 기준 시간보다 오래된 INIT Outbox | HIGH |
| `OUTBOX_STATE_MISMATCH` | Outbox와 결제·취소 최종 상태가 모순 | HIGH |
| `PG_TRANSACTION_ID_MISSING` | PG 처리가 필요한 완료 건에 외부 거래 ID 없음 | HIGH |
| `PG_RESPONSE_LOG_MISSING` | PG 처리 건의 응답 로그 없음 | MEDIUM |

동일 업무 식별자에 여러 불일치가 동시에 존재할 수 있으므로 유형별 Case를 독립 저장한다.

## 5. 상태와 조치 모델

### 5.1 실행 상태

`ReconciliationRunStatus`:

- `RUNNING`: 검사 진행 중
- `COMPLETED`: 범위 전체 검사 완료
- `PARTIALLY_FAILED`: 일부 검사기는 실패했으나 나머지 결과 저장 완료
- `FAILED`: 실행 자체가 완료되지 못함

### 5.2 Case 상태

`ReconciliationCaseStatus`:

- `OPEN`: 새 불일치
- `INVESTIGATING`: 운영 분석 중
- `ACTION_REQUIRED`: 외부 또는 수동 조치 필요
- `RESOLVED`: 재검증으로 일치 확인
- `FALSE_POSITIVE`: 승인된 오탐

`RESOLVED`는 운영자가 임의로 선택할 수 없고 재검증 결과가 정상일 때만 전환한다. `FALSE_POSITIVE`는 사유와 운영자 식별자가 필수다.

### 5.3 조치 유형

`ReconciliationActionType`:

- `START_INVESTIGATION`
- `REQUEST_PG_CONFIRMATION`
- `REQUEST_MANUAL_LEDGER_REVIEW`
- `MARK_FALSE_POSITIVE`
- `RECHECK`
- `CONFIRM_RESOLVED`

수동 DB UPDATE 문이나 원장 변경 payload는 조치 이력에 저장하지 않는다. 외부 티켓·승인 문서 식별자와 안전한 설명만 기록한다.

| 컬럼 | 제약 | 설명 |

| 컬럼 | 제약 | 설명 |
| --- | --- | --- |
| `id` | PK | Case 식별자 |

| `evidence` | CLOB, NOT NULL | 버전이 있는 안전한 JSON 근거 |
| `first_detected_at`, `last_detected_at` | NOT NULL | 최초·최근 탐지 시각 |

## 8. Detector 계획

- `WalletBalanceDetector`
  - 지갑 생성 이후 거래 합계를 계산하고 현재 잔액과 비교한다.
- `PaymentWalletDetector`
  - 완료 결제와 PAYMENT 거래의 존재·금액·paymentId를 비교한다.
- `CancellationWalletDetector`
  - 완료 취소와 REFUND 거래의 존재·금액·cancelId를 비교한다.
- `CancellationAccumulationDetector`
  - 완료 취소 합계, 결제 누적 취소 금액과 원 결제 금액 상한을 비교한다.
- `PendingTimeoutDetector`
  - 설정된 기준 시간을 초과한 결제·취소 PENDING을 탐지한다.
- `OutboxConsistencyDetector`
  - 장기 INIT과 Outbox·업무 상태 모순을 탐지한다.
- `PgTraceDetector`
  - 외부 거래 식별자와 PG 응답 로그 존재 여부를 확인한다.

각 Detector는 독립 트랜잭션·페이지 단위로 실행한다. 하나가 실패해도 다른 Detector는 계속 실행하고 Run을 `PARTIALLY_FAILED`로 기록한다.

## 9. 불일치 발생 시 조치 절차

1. Detector가 불일치와 비교 근거를 생성한다.
2. `caseKey = mismatchType + business identifiers`로 기존 Case를 조회한다.
3. 신규이면 `OPEN`, 기존 미해결 Case이면 `lastDetectedAt`과 evidence를 갱신한다.
4. 운영자는 Case를 `INVESTIGATING`으로 전환하고 담당 티켓을 연결한다.
5. PG 확인, 원장 검토 또는 Outbox 재처리 같은 조치는 기존 승인된 업무 절차를 통해 수행한다.
6. 조치 완료 후 운영자가 `RECHECK`를 요청한다.
7. 동일 Detector가 대상만 다시 검사한다.
8. 일치하면 시스템이 `RESOLVED`로 전환하고 해결 시각을 기록한다.
9. 여전히 불일치하면 `ACTION_REQUIRED`로 유지하고 최신 근거를 저장한다.
10. 모든 조회·상태 전이·재검증 요청은 감사 로그에 기록한다.

원장 직접 수정이 불가피한 상황은 이 기능이 실행하지 않는다. 별도 장애 조치 Runbook, 변경 승인, 백업, 검증 SQL 및 사후 대사를 거쳐 운영자가 수행하며 참조 티켓만 Case에 연결한다.

## 10. API 계획

- `POST /api/v1/ops/reconciliations/runs`
  - 수동 검사 범위 실행 요청
- `GET /api/v1/ops/reconciliations/runs`
  - 실행 이력 검색
- `GET /api/v1/ops/reconciliations/runs/{runId}`
  - 실행 통계·검사기 실패 조회
- `GET /api/v1/ops/reconciliation-cases`
  - 유형, 심각도, 상태, 업무 식별자, 탐지 기간 검색
- `GET /api/v1/ops/reconciliation-cases/{caseId}`
  - 근거와 조치 이력 조회
- `POST /api/v1/ops/reconciliation-cases/{caseId}/actions`
  - 허용된 운영 상태 전이·사유 등록
- `POST /api/v1/ops/reconciliation-cases/{caseId}/recheck`
  - 단건 재검증 요청

API는 삭제 endpoint와 원장 보정 endpoint를 제공하지 않는다. 인증 구현 전에는 운영 API를 외부에 공개하지 않는다.

## 11. 동시성 및 멱등성

- 동일 `runKey`의 실행 요청은 기존 Run을 반환한다.
- Scheduler 중복 실행은 DB 선점 또는 분산 잠금으로 차단한다.
- Case upsert는 `caseKey` unique constraint와 DB 충돌 재조회로 멱등 처리한다.
- 운영 상태 전이는 `@Version` 낙관적 잠금을 사용한다.
- 같은 Case의 동시 재검증은 실행 중 플래그 또는 선점 테이블로 한 건만 허용한다.
- 대사 조회는 원장 행을 수정 잠금하지 않고 일관된 범위 기준시각을 사용한다.

- `reconciliation.run.count{status,trigger}`
- `reconciliation.run.duration`
- `reconciliation.checked.count{detector}`

## 13. 테스트 계획

### 13.1 단위 테스트

- Run 상태와 완료 통계 불변식
- Case 상태 전이와 해결 조건
- 운영 조치 사유·외부 참조 검증
- 유형별 Detector 정상·불일치 판정
- caseKey/runKey 결정성
- 같은 Finding 반복 적용의 멱등성

### 13.2 Repository 통합 테스트

- 기간·상태·유형·업무 식별자 검색
- caseKey/runKey unique 충돌
- 낙관적 잠금 충돌
- evidence 민감 필드 비포함
- DDL comment, 제약 및 인덱스 검증

### 13.3 업무 통합 테스트

- 정상 결제·취소·지갑 데이터에서 불일치 0건
- 각 불일치 유형별 변조 fixture 탐지
- 일부 Detector 실패 후 `PARTIALLY_FAILED` 및 나머지 결과 유지
- 운영 조치 후 재검증 해결
- 미해결 재검증 시 `ACTION_REQUIRED` 유지
- 대사 실행 전후 업무 원장 값 불변
- 같은 범위 반복 실행 시 Run·Case 중복 방지
- 대사 Worker 중단·재기동 후 안전한 재개

### 13.4 인수 및 장애 테스트

- 온라인 API 부하 중 대사 실행이 결제 응답과 잠금을 방해하지 않음
- DB 일시 장애 후 Run 실패 추적과 재실행 가능
- 대사 Worker 다중 인스턴스에서 실행 중복 없음
- 대규모 페이지 검사 중 메모리 상한과 DB 커넥션 안정성
- CRITICAL Case의 운영 조회·감사 로그·알림 연결

## 14. 구현 순서

1. `outbox-worker` 분리와 장애 검증을 완료한다.
2. 대사 ADR에서 기준시각, DB 선점, PG 기준 데이터와 운영 승인 정책을 확정한다.
3. Flyway DDL과 Domain Entity·enum을 구현한다.
4. Run·Case·Action Repository와 통합 테스트를 구현한다.
5. Detector SPI, Registry와 유형별 Detector를 구현한다.
6. 실행 orchestration, 멱등 upsert와 부분 실패 격리를 구현한다.
7. 운영 조회·조치·재검증 API와 Swagger 계약을 구현한다.
8. Scheduler, health, metric과 운영 알림 기반을 구현한다.
9. 전체 단위·통합·인수·장애 테스트와 JaCoCo를 실행한다.
10. API 명세, 아키텍처, Runbook과 대화 기록을 현행화한다.

## 15. 완료 기준

- 정의된 모든 불일치 유형을 정상 데이터 오탐 없이 탐지한다.
- 동일 범위 반복 실행과 동일 Finding 처리에서 중복 Run·Case가 발생하지 않는다.
- 불일치 근거, 상태, 운영 조치 및 재검증 이력이 추적된다.
- 해결 상태는 정상 재검증을 거쳐서만 확정된다.
- 대사 기능이 결제·지갑·취소 원장을 자동 변경하지 않는다.
- 대사 실패가 온라인 API와 Outbox Worker를 중단시키지 않는다.
- 민감정보, PG 원문, 암호문과 멱등키가 evidence·로그·metric에 노출되지 않는다.
- OpenAPI, 단위·통합·인수·ArchUnit 테스트와 JaCoCo 리포트가 통과한다.

## 16. 승인 요청 사항

1. 대사 1단계는 탐지·운영 보고·조치 이력·재검증만 구현
2. 자동 원장 보정, 자동 PG 조치와 데이터 삭제 API 제외
3. `reconciliation_run`, `reconciliation_case`, `reconciliation_action_history` 별도 원장 사용
4. Case 해결은 정상 재검증으로만 확정
5. Detector 부분 실패를 격리하고 Run은 `PARTIALLY_FAILED`로 추적
6. `outbox-worker` 분리 완료 후 대사 구현 시작
