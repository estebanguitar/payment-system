## 3. 세션 기록 (2026-08-09)

### 3.1 도메인 레이어 구현계획 수립 요청

- 사용자는 상세 아키텍처 정의서를 기준으로 도메인 레이어의 구현계획 작성을 요청했다.
- 요구사항 정의서, API 명세, ADR 0001~0003, Flyway 스키마, Lombok 코딩 컨벤션 및 현재 소스 구조를 함께 검토했다.
- 구현 범위를 엔티티, 열거형, 도메인 예외, 도메인 단위 테스트 및 JPA 매핑 테스트로 한정하고 Application·Presentation·Infrastructure 구현은 후속 단계로 분리했다.
- 코드 수준의 패키지·파일 구성, Aggregate 경계, 생성 팩터리, 상태 전이 메서드, 금액 불변식, 테스트 및 완료 기준을 `docs/in-progress-deliverables/002-도메인-레이어-구현계획.md`에 작성했다.
- 계획은 사용자 승인 대기 상태이며 승인 전에는 구현, 커밋, 푸시 및 PR 생성을 진행하지 않는다.

### 3.2 구현 전 확인이 필요한 정합성 항목

1. 요구사항의 “시스템 전체 멱등키 유일” 정책과 현재 테이블별 UNIQUE 제약 사이에 차이가 있어 별도 글로벌 멱등성 원장 도입 또는 요구사항 변경 결정이 필요하다.
2. 동일 결제의 동시 부분 취소 시 누적 취소액 초과를 막기 위해 원 결제에도 비관적 쓰기 잠금을 적용할 필요가 있다.
3. 취소 실패 사유가 별도 enum으로 정의되지 않아 결제 실패 사유 재사용 여부를 구현 전 확정해야 한다.

### 3.3 Flyway DDL 컬럼 설명 추가

- 사용자는 스키마 DDL의 각 컬럼에 설명을 추가하도록 요청했다.
- `V1__init_schema.sql`의 7개 테이블 전체 컬럼에 H2 호환 `COMMENT ON COLUMN` 문법으로 한글 설명을 추가하는 계획을 제안했고 사용자가 승인했다.
- 현재 1페이즈는 재시작 시 초기화되는 H2 인메모리 DB를 사용하므로 별도 증분 마이그레이션을 생성하지 않고 초기 스키마 V1을 보완하기로 했다.
- 최초에는 별도 `COMMENT ON COLUMN` 문으로 작성했으나, 사용자가 테이블 정의를 읽는 즉시 설명을 확인할 수 있도록 요청하여 각 `CREATE TABLE`의 컬럼 정의에 인라인 `COMMENT`를 배치하는 방식으로 변경했다.

### 3.4 코드 주석 협업 규칙 추가

- 도메인 레이어 구현 중 사용자는 협업자가 코드 의도를 쉽게 파악할 수 있도록 클래스와 메서드에 간단한 설명 주석을 작성하도록 요청했다.
- `AGENTS.md`와 코딩 컨벤션에 클래스 책임 및 메서드 기능·주요 제약을 간결하게 문서화하는 규칙을 추가했다.
- 공개 API와 도메인 메서드는 Javadoc을 우선하고, 구현을 그대로 반복하는 불필요한 주석은 제외하기로 했다.

### 3.5 Swagger/OpenAPI 명세 요구사항 추가

- 사용자는 Swagger를 사용해 API 명세서를 작성하도록 요구사항 정의서 수정을 요청했다.
- Swagger UI/OpenAPI 3 기반의 명세 자동 생성과 개발 환경 호출 기능을 Must 요구사항 `API-002`로 추가했다.
- 요청·응답 모델, `Idempotency-Key`, 경로·쿼리 파라미터, 공통 응답 및 주요 오류 코드를 문서화하도록 인수 기준을 정의했다.
- 실제 `springdoc-openapi` 의존성 및 Controller 문서화는 후속 Presentation/API 계층 구현 범위로 분리했다.

### 3.6 도메인 오류 코드 및 메시지 표준화

- 사용자는 오류 코드와 메시지를 enum으로 정의해 여러 도메인 예외에서 재사용하도록 요청했다.
- `DomainErrorCode`에 업무 오류 코드와 표준 메시지를 함께 정의하고 `DomainException`이 해당 enum을 보유하도록 변경했다.
- 엔티티에 흩어진 문자열 오류 메시지와 일반 입력 예외를 표준 도메인 오류로 교체하고 코드·메시지 재사용 테스트를 추가했다.

### 3.7 도메인 레이어 구현 완료

- 사용자가 도메인 레이어 구현계획을 승인하여 `feature/domain-layer` 브랜치를 생성하고 구현을 진행했다.
- Customer, Wallet, WalletTransaction, Payment, PaymentCancel, PgResponseLog, PaymentOutbox 및 관련 enum·도메인 예외를 구현했다.
- Aggregate 간 연관관계는 식별자 참조로 유지하고, 공개 Setter 없이 도메인 메서드로 상태와 금액 불변식을 통제했다.
- 엔티티 필드에 `final`을 사용하지 않은 이유는 JPA 식별자 주입, 프록시·dirty checking 및 결제·잔액 상태 변경 생명주기와의 호환성 때문임을 사용자에게 설명했다.
- 전체 25개 테스트가 실패와 오류 없이 통과했으며 JPA/Flyway 매핑 및 DDL 컬럼 설명 메타데이터도 함께 검증했다.

### 3.11 대규모 트래픽 대비 부하 테스트 요구사항 정의

- 사용자는 대규모 트래픽 유입에 대비한 부하 테스트 요구사항을 요구사항 정의서에 추가하도록 요청했다.
- 일반 지속 부하, 순간 급증, 동일 지갑 집중 경합, 외부 PG 지연·타임아웃 및 조회 집중 부하를 필수 시나리오로 정의했다.
- 1페이즈 기본 프로파일은 워밍업 후 100 동시 사용자의 10분 지속 부하, 최대 500 동시 사용자의 순간 급증 및 동일 지갑 100개 동시 결제로 정했다.
- 시스템 오류율 1% 미만, 데이터 정합성 위반 0건 및 부하 종료 후 정상 회복을 1페이즈 판정 기준으로 정했다.
- H2·단일 인스턴스 결과는 운영 용량 보장이 아닌 회귀 비교 기준선으로 사용하며, 실제 운영 환경 용량 산정은 2페이즈로 분리했다.
- 사용자 후속 요청에 따라 부하 테스트 실행 시점을 모든 계층의 개발사항과 기능·통합·인수 테스트가 완료된 이후의 최종 시스템 검증 단계로 변경했다. 인프라스트럭처 레이어에서는 부하 테스트를 실행하지 않고 잠금·커넥션·PG 지연을 측정할 기반만 제공한다.

### 3.13 인프라스트럭처 레이어 구현 완료

- 사용자가 구현계획을 승인하여 merge commit `9f3ee60` 기반 `feature/infrastructure-layer` 브랜치를 생성하고 구현했다.
- 도메인별 Spring Data JPA Repository, V3 글로벌 멱등성 저장소, 지갑·원 결제 비관적 잠금, 결정적 가상 PG, AES-256-GCM 암호화 및 조건부 아웃박스 스케줄러 기반을 추가했다.
- 글로벌 멱등키 동시 선점은 두 트랜잭션 중 하나만 성공하고, 지갑·원 결제 잠금은 선행 트랜잭션 종료까지 후속 트랜잭션이 대기하는 것을 H2 통합 테스트로 확인했다.
- 가상 PG는 실제 sleep이나 확률 없이 승인·거절·오류·타임아웃을 재현하며 동일 멱등키에 결정적인 거래 ID를 반환한다.
- 테스트 프로파일 파일에 고정 암호화 키를 저장하는 대신 조건부 Bean 테스트에 테스트 키를 한정하여 계획 대비 보안을 강화했다.
- 전체 56개 테스트가 통과했고 JaCoCo 기준 라인 89.25%, 브랜치 67.89%, 메서드 97.27%, 클래스 100%를 확인했다.
- 부하 테스트는 모든 개발 완료 후 최종 시스템 검증 단계에서 수행하기로 한 요구사항에 따라 실행하지 않았다.

### 3.15 프로젝트 완료 후 사용자 직접 테스트 문서 작성 요구

- 사용자 테스트 문서는 개발 중간에 작성하지 않고 모든 기능 개발, 자동화 테스트 및 최종 부하 테스트가 완료된 뒤 최종 인수·인계 단계에서 작성하도록 `QUA-003` Must 요구사항으로 추가했다.

- 사용자 테스트 문서는 프로젝트 완료 시점의 커밋 SHA와 실제 Swagger/OpenAPI 명세를 기준으로 `docs/completion-deliverables/`에 작성한다.

### 3.16 애플리케이션 레이어 구현계획 수립

- 사용자는 인프라스트럭처 구현 다음 단계로 Application 레이어 구현계획 작성을 요청했다.
- 지갑, 결제, 취소, 조회, 글로벌 멱등성, Spring AFTER_COMMIT 이벤트 및 아웃박스 복구를 Application 유스케이스 범위로 정의했다.
- 외부 PG 호출 중 DB 트랜잭션을 보유하지 않고 PENDING 원장 커밋 후 동기 AFTER_COMMIT Listener에서 호출하며, 결과는 별도 Transactional Service가 반영하도록 Bean과 트랜잭션 경계를 분리했다.
- 취소도 JVM 장애 복구 대상에 포함하도록 기존 payment_outbox에 `PAYMENT_CANCEL_REQUESTED` 이벤트를 추가하는 방안을 계획했다.
- PG·암호화·아웃박스 복구 인터페이스를 Application 포트로 이동하여 의존성 방향을 보정하도록 계획했다.
- 전체 시스템 부하 테스트와 사용자 직접 테스트 문서 작성은 모든 개발 및 내부 검증 완료 후 단계로 유지했다.
- 코드 파일 구성, 업무별 처리 순서, 트랜잭션 전파, 테스트 및 완료 기준을 `docs/in-progress-deliverables/004-애플리케이션-레이어-구현계획.md`에 작성했으며 현재 사용자 승인 대기 상태다.

### 3.17 Fake PG 승인 원문 결정성 리뷰 반영

- PR #2 리뷰에서 `Map.of`의 순회 순서가 명세상 보장되지 않아 동일 요청의 JSON 필드 순서가 달라질 수 있다는 의견이 제기됐다.
- 승인 응답 payload도 취소 응답과 동일하게 `LinkedHashMap` 삽입 순서로 직렬화하도록 변경했다.
- 동일 요청의 PG 거래 ID와 rawPayload 문자열 전체 및 필드 순서가 반복 호출에서 동일한지 회귀 테스트를 추가했다.
