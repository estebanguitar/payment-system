## 3. 세션 기록 (2026-08-09)

### 3.1 도메인 레이어 구현계획 수립 요청

- 사용자는 상세 아키텍처 정의서를 기준으로 도메인 레이어의 구현계획 작성을 요청했다.
- 요구사항 정의서, API 명세, ADR 0001~0003, Flyway 스키마, Lombok 코딩 컨벤션 및 현재 소스 구조를 함께 검토했다.
- 구현 범위를 엔티티, 열거형, 도메인 예외, 도메인 단위 테스트 및 JPA 매핑 테스트로 한정하고 Application·Presentation·Infrastructure 구현은 후속 단계로 분리했다.
- 코드 수준의 패키지·파일 구성, Aggregate 경계, 생성 팩터리, 상태 전이 메서드, 금액 불변식, 테스트 및 완료 기준을 `docs/in-progress-deliverables/002-도메인-레이어-구현계획.md`에 작성했다.
- 계획은 사용자 승인 대기 상태이며 승인 전에는 구현, 커밋, 푸시 및 PR 생성을 진행하지 않는다.

### 3.2 구현 전 확인이 필요한 정합성 항목

1. 요구사항의 “시스템 전체 멱등키 유일” 정책과 현재 테이블별 UNIQUE 제약 사이에 차이가 있어 별도 글로벌 멱등성 원장 도입 또는 요구사항 변경 결정이 필요하다.
2. 동일 결제의 동시 부분 취소 시 누적 취소액 초과를 막기 위해 원 결제에도 비관적 쓰기 잠금을 적용할 필요가 있다.
3. 취소 실패 사유가 별도 enum으로 정의되지 않아 결제 실패 사유 재사용 여부를 구현 전 확정해야 한다.

### 3.3 Flyway DDL 컬럼 설명 추가

- 사용자는 스키마 DDL의 각 컬럼에 설명을 추가하도록 요청했다.
- `V1__init_schema.sql`의 7개 테이블 전체 컬럼에 H2 호환 `COMMENT ON COLUMN` 문법으로 한글 설명을 추가하는 계획을 제안했고 사용자가 승인했다.
- 현재 1페이즈는 재시작 시 초기화되는 H2 인메모리 DB를 사용하므로 별도 증분 마이그레이션을 생성하지 않고 초기 스키마 V1을 보완하기로 했다.
- 최초에는 별도 `COMMENT ON COLUMN` 문으로 작성했으나, 사용자가 테이블 정의를 읽는 즉시 설명을 확인할 수 있도록 요청하여 각 `CREATE TABLE`의 컬럼 정의에 인라인 `COMMENT`를 배치하는 방식으로 변경했다.

### 3.4 코드 주석 협업 규칙 추가

- 도메인 레이어 구현 중 사용자는 협업자가 코드 의도를 쉽게 파악할 수 있도록 클래스와 메서드에 간단한 설명 주석을 작성하도록 요청했다.
- `AGENTS.md`와 코딩 컨벤션에 클래스 책임 및 메서드 기능·주요 제약을 간결하게 문서화하는 규칙을 추가했다.
- 공개 API와 도메인 메서드는 Javadoc을 우선하고, 구현을 그대로 반복하는 불필요한 주석은 제외하기로 했다.

### 3.5 Swagger/OpenAPI 명세 요구사항 추가

- 사용자는 Swagger를 사용해 API 명세서를 작성하도록 요구사항 정의서 수정을 요청했다.
- Swagger UI/OpenAPI 3 기반의 명세 자동 생성과 개발 환경 호출 기능을 Must 요구사항 `API-002`로 추가했다.
- 요청·응답 모델, `Idempotency-Key`, 경로·쿼리 파라미터, 공통 응답 및 주요 오류 코드를 문서화하도록 인수 기준을 정의했다.
- 실제 `springdoc-openapi` 의존성 및 Controller 문서화는 후속 Presentation/API 계층 구현 범위로 분리했다.

### 3.6 도메인 오류 코드 및 메시지 표준화

- 사용자는 오류 코드와 메시지를 enum으로 정의해 여러 도메인 예외에서 재사용하도록 요청했다.
- `DomainErrorCode`에 업무 오류 코드와 표준 메시지를 함께 정의하고 `DomainException`이 해당 enum을 보유하도록 변경했다.
- 엔티티에 흩어진 문자열 오류 메시지와 일반 입력 예외를 표준 도메인 오류로 교체하고 코드·메시지 재사용 테스트를 추가했다.

### 3.7 도메인 레이어 구현 완료

- 사용자가 도메인 레이어 구현계획을 승인하여 `feature/domain-layer` 브랜치를 생성하고 구현을 진행했다.
- Customer, Wallet, WalletTransaction, Payment, PaymentCancel, PgResponseLog, PaymentOutbox 및 관련 enum·도메인 예외를 구현했다.
- Aggregate 간 연관관계는 식별자 참조로 유지하고, 공개 Setter 없이 도메인 메서드로 상태와 금액 불변식을 통제했다.
- 엔티티 필드에 `final`을 사용하지 않은 이유는 JPA 식별자 주입, 프록시·dirty checking 및 결제·잔액 상태 변경 생명주기와의 호환성 때문임을 사용자에게 설명했다.
- 전체 25개 테스트가 실패와 오류 없이 통과했으며 JPA/Flyway 매핑 및 DDL 컬럼 설명 메타데이터도 함께 검증했다.

### 3.11 대규모 트래픽 대비 부하 테스트 요구사항 정의

- 사용자는 대규모 트래픽 유입에 대비한 부하 테스트 요구사항을 요구사항 정의서에 추가하도록 요청했다.
- 일반 지속 부하, 순간 급증, 동일 지갑 집중 경합, 외부 PG 지연·타임아웃 및 조회 집중 부하를 필수 시나리오로 정의했다.
- 1페이즈 기본 프로파일은 워밍업 후 100 동시 사용자의 10분 지속 부하, 최대 500 동시 사용자의 순간 급증 및 동일 지갑 100개 동시 결제로 정했다.
- 시스템 오류율 1% 미만, 데이터 정합성 위반 0건 및 부하 종료 후 정상 회복을 1페이즈 판정 기준으로 정했다.
- H2·단일 인스턴스 결과는 운영 용량 보장이 아닌 회귀 비교 기준선으로 사용하며, 실제 운영 환경 용량 산정은 2페이즈로 분리했다.
- 사용자 후속 요청에 따라 부하 테스트 실행 시점을 모든 계층의 개발사항과 기능·통합·인수 테스트가 완료된 이후의 최종 시스템 검증 단계로 변경했다. 인프라스트럭처 레이어에서는 부하 테스트를 실행하지 않고 잠금·커넥션·PG 지연을 측정할 기반만 제공한다.

### 3.13 인프라스트럭처 레이어 구현 완료

- 사용자가 구현계획을 승인하여 merge commit `9f3ee60` 기반 `feature/infrastructure-layer` 브랜치를 생성하고 구현했다.
- 도메인별 Spring Data JPA Repository, V3 글로벌 멱등성 저장소, 지갑·원 결제 비관적 잠금, 결정적 가상 PG, AES-256-GCM 암호화 및 조건부 아웃박스 스케줄러 기반을 추가했다.
- 글로벌 멱등키 동시 선점은 두 트랜잭션 중 하나만 성공하고, 지갑·원 결제 잠금은 선행 트랜잭션 종료까지 후속 트랜잭션이 대기하는 것을 H2 통합 테스트로 확인했다.
- 가상 PG는 실제 sleep이나 확률 없이 승인·거절·오류·타임아웃을 재현하며 동일 멱등키에 결정적인 거래 ID를 반환한다.
- 테스트 프로파일 파일에 고정 암호화 키를 저장하는 대신 조건부 Bean 테스트에 테스트 키를 한정하여 계획 대비 보안을 강화했다.
- 전체 56개 테스트가 통과했고 JaCoCo 기준 라인 89.25%, 브랜치 67.89%, 메서드 97.27%, 클래스 100%를 확인했다.
- 부하 테스트는 모든 개발 완료 후 최종 시스템 검증 단계에서 수행하기로 한 요구사항에 따라 실행하지 않았다.

### 3.29 감사 로그 승인과 재현 가능한 컨테이너 실행 요구

- 사용자는 감사 로그 계획에서 삭제 API, 자동 삭제 및 보존 만료 삭제를 제외하고 나머지 설계를 승인했다.
- 감사 로그 계획과 ADR-004를 승인 상태로 변경하고 삭제 관련 서비스·Repository·Scheduler·테스트를 구현 범위에서 제거했다.
- 사용자는 개발 PC와 서버에서 동일한 실행을 보장하도록 Dockerfile과 Docker Compose 구성을 요청했다.
- Java 17 멀티 스테이지 이미지, Docker 전용 파일 기반 H2 설정, named volume, 고정 포트·시간대·문자 인코딩 및 실행 안내를 `QUA-005` 요구사항으로 반영했다.
- 코드 타입은 패키지 경로를 본문에 직접 작성하지 않고 import로 참조하며 static import를 지양하는 협업 규칙을 `AGENTS.md`에 추가했다.

### 3.30 패키지 구조 개선 선행 및 Outbox Worker·잔고 대사 후속 요구

- 사용자는 도메인 우선 패키지 구조 개선을 먼저 완료하고 실행 모듈 분리와 신규 업무 기능을 같은 변경에 포함하지 않도록 요청했다.
- 패키지 구조 개선 단계에서는 Outbox 코드를 최상위 도메인 경계로 응집하되 기존 실행 방식과 트랜잭션을 유지한다.
- 구조 개선 병합 후 Scheduler, 고립 이벤트 복구, PG 후속 처리를 `outbox-worker` 독립 Gradle 모듈·배포 프로세스로 분리하는 `ARC-001`~`ARC-003`을 Must 요구사항으로 추가했다.
- API 프로세스 중단 중에도 DB와 PG가 가용하면 Worker 처리가 지속되어야 하며, 다중 Worker 선점·중복 방지·heartbeat·재시도·poison event 격리를 후속 구현 범위로 정했다.
- Worker 분리 후 결제·지갑·취소·PG·Outbox 불일치를 탐지하는 잔고·원장 대사 기능 `REC-001`~`REC-003`을 구현한다.
- 대사 1단계는 탐지와 운영 보고만 제공하고 자동 보정은 금전 오류 위험 때문에 별도 요구사항과 승인을 받기 전까지 제외한다.

### 3.31 도메인 우선 패키지 구조 개선 구현

- PR #5 병합 후 `refactor/domain-first-package-structure` 브랜치를 생성하고 합의한 개선계획 문서를 최초 커밋으로 생성했다.
- Outbox Worker와 잔고·원장 대사는 후속 요구사항 커밋으로 분리해 패키지 이동과 기능 변경이 섞이지 않도록 했다.
- shared·audit, customer·pg, wallet·idempotency, payment·cancellation, outbox 순서로 이동하고 각 단계마다 compile과 전체 회귀 테스트를 수행해 독립 커밋했다.
- Outbox는 기존 Scheduler·재처리·재시도 동작을 유지한 채 패키지만 응집했으며 독립 Worker 분리는 수행하지 않았다.
- 이동 후 비어 있는 패키지 디렉터리를 제거하고 공통 설정과 다중 도메인 통합 테스트를 shared·architecture 경계로 이동했다.
- ArchUnit 1.4.2를 추가해 구 역할 우선 패키지 재생성, Domain의 상위 계층 의존과 Controller의 Repository 직접 의존을 자동 차단했다.
- 공개 API·DDL·Flyway·트랜잭션 변경 없이 `clean test jacocoTestReport bootJar`가 성공함을 확인했다.

### 3.32 잔고 및 원장 불일치 조치방안 구현계획 수립

- 사용자는 패키지 구조 개선 완료 후 잔고 대사와 원장 불일치 발생 시 조치방안의 구현계획 작성을 요청했다.
- 대사는 결제·지갑·취소·PG·Outbox 불일치를 별도 Worker에서 탐지하고 실행·Case·조치 이력을 독립 원장으로 관리하도록 계획했다.
- 1단계는 탐지, 운영 판정, 수동 조치 참조 및 재검증만 제공하며 결제·지갑·취소 원장의 자동 수정과 PG 자동 조치는 제외했다.
- Case는 정상 재검증을 거쳐서만 `RESOLVED`로 전환하고 오탐 판정에는 운영자와 사유를 필수로 남기도록 했다.
- 상세 파일, DDL, Detector, API, 동시성·멱등성, 모니터링 및 테스트 계획은 `008-잔고-및-원장-대사-구현계획.md`에 정의했다.

### 3.33 잔고 및 원장 대사 1단계 구현

- 사용자는 PR #6 병합 후 Outbox Worker 분리와 잔고 대사를 별도 브랜치·PR로 병렬 구현하도록 승인했다.
- 대사는 Outbox Worker 구현체에 결합하지 않고 `ReconciliationExecutionPort`를 통해 수동 API와 향후 독립 Batch가 같은 실행 계약을 사용하도록 구현했다.
- 실행·Case·조치 이력 원장, 범위 멱등 키, 낙관적 잠금, Detector 부분 실패 격리 및 Micrometer 지표를 추가했다.
- 지갑 잔액, 결제 차감, 취소 누적·환불, 장기 PENDING, 장기 INIT, PG 응답 로그를 읽기 전용으로 교차 검증한다.
- 운영 API는 조회·판정·재검증만 제공하며 자동 원장 수정, 자동 PG 조치와 삭제 API는 제공하지 않는다.

### 3.34 PR #7 추가 리뷰 반영

- 동일 범위의 동시 최초 요청은 독립 트랜잭션에서 실행 원장을 즉시 선점하고, 고유 키 경합에서 패배한 요청은 기존 Run을 반환하도록 보강했다.
- 실행 Trigger를 입력 Port 계약에 포함해 수동 실행과 향후 스케줄 실행을 구분하며, 검사기 실패 원인을 이름과 예외 로그로 남긴다.
- Case 재검증은 불일치 유형을 지원하는 검사기만 실행하고, 검사 실패 또는 담당 검사기 부재 시 해결로 오판하지 않도록 `ACTION_REQUIRED`를 유지한다.
- 지갑 대사는 요청 범위에 거래가 발생한 지갑만 집계 대상으로 제한해 매 실행의 전체 지갑 스캔을 방지한다.

### 3.34 MVP 범위 재정의와 레이어드 모놀리스 회귀

- 사용자는 현재 시스템 규모에 비해 독립 Outbox Worker, 잔고 대사 및 도메인별 Clean Architecture 반복 구조가 과도하다고 판단했다.
- 결제·취소 원장과 Outbox를 동일 트랜잭션으로 커밋하고 `AFTER_COMMIT` Listener가 즉시 처리하며, 같은 프로세스 Scheduler가 남은 `PENDING/RETRY`만 복구하는 구조로 축소하기로 했다.
- 감사 기능은 누가 어떤 URL을 언제 호출했고 request와 response가 무엇이었는지를 저장하는 최소 API 요청 이력으로 한정했다.
- 감사 조회·삭제·보존 자동화는 제외하고 요청·응답 및 민감정보는 AES-256-GCM으로 암호화해 저장하되 token·password처럼 복호화할 필요가 없는 secret은 사전 제거하기로 했다.
- 패키지는 멀티모듈·MSA를 미리 가정하지 않고 `domain`, `repository`, `service`, `controller`, `dto`, `integration`, `scheduler`, `common` 중심의 단일 Spring Boot 레이어드 구조로 단순화한다.
- 잔고·원장 대사 런타임 기능은 제거하되 이미 병합된 Flyway migration은 checksum 안전성을 위해 수정하지 않는 구현계획을 수립했다.
- 사용자는 모든 후속 문서와 구현 작업을 별도 브랜치가 아닌 `main`에서 진행하도록 지정했다.
- Case와 조치 이력의 DB 필수값을 도메인 생성 시점에 검증하고, 재탐지 시 심각도·관련 식별자·근거를 최신 값으로 갱신한다.

### 3.36 MVP 단순화 구현

- 사용자는 `009-MVP-단순화-및-레이어드-아키텍처-전환-구현계획.md`를 승인하고 `main`에서 구현하도록 요청했다.
- 구현 중 결제 후 취소 금지 요구를 잠시 제시했으나 즉시 철회했으므로 기존 전액·부분 취소와 환불 기능을 유지했다.
- 잔고 대사와 감사 조회 API를 제거하고 API 요청·응답 감사 원문을 AES-256-GCM으로 암호화해 저장하도록 변경했다.
- 패키지를 간결한 레이어드 구조로 이동하고 Outbox 상태를 `PENDING/RETRY/COMPLETED/FAILED`로 명확히 했다.
