## 2. 목표와 범위

### 2.1 목표

- 성공·실패 여부와 무관하게 외부 클라이언트의 API 요청 결과를 추적한다.
- 기간, 클라이언트 식별자, 정규화 경로, 상태 코드 및 추적 ID로 운영 검색을 제공한다.
- 감사 데이터는 추가 전용으로 관리하고 일반 업무 수정 흐름에서 변경·삭제하지 않는다.
- 요청·응답 본문, 인증정보, 멱등키 및 개인정보가 감사 로그에 저장되지 않도록 허용 목록 방식으로 수집한다.
- 감사 저장 실패를 탐지할 수 있는 지표와 비상 로그를 제공한다.

### 2.2 구현 범위

- 요청 추적 ID 생성·전파
- Servlet Filter 기반 요청 완료 감사 이벤트 수집
- 별도 트랜잭션을 사용하는 감사 로그 저장 서비스
- 감사 로그 테이블, 인덱스 및 추가 전용 Repository
- 운영자 감사 로그 검색·단건 조회 API
- 민감정보 비수집 및 경로·식별자 정규화
- 단위·통합·HTTP·OpenAPI 테스트

### 2.3 제외 범위

- 인증·인가 체계 자체의 구현
- 요청·응답 본문 원문 저장과 재현
- 외부 SIEM, Kafka 또는 별도 로그 클러스터 도입
- 감사 로그를 이용한 실시간 차단·이상 탐지
- 모든 개발 완료 전에 수행하는 공식 부하 테스트

## 3. 핵심 설계 결정

### 3.1 수집 경계

`OncePerRequestFilter`의 `try/finally`에서 요청 시작·종료 시각과 최종 HTTP 상태를 수집한다. Controller AOP는 바인딩 실패, 404, 필터 단계 오류를 놓칠 수 있으므로 주 수집 수단으로 사용하지 않는다. 정규화 경로는 요청 완료 후 `HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE`를 우선 사용하고, 매핑되지 않은 요청만 안전하게 정규화한 URI를 사용한다.

### 3.2 저장 정합성과 가용성

1페이즈는 인메모리 비동기 큐를 사용하지 않는다. 요청 처리 트랜잭션과 분리된 `REQUIRES_NEW` 트랜잭션으로 감사 로그를 저장해 업무 롤백과 무관하게 성공·실패 이력을 남긴다. 저장은 응답 커밋 전에 완료하되 감사 저장 실패가 이미 완료된 결제·충전 결과를 뒤집지는 않는다. 실패 시 payload 없는 보안 비상 로그와 실패 카운터를 남긴다.

DB 전체 장애에서는 업무 결과와 감사 로그를 동시에 완전 보장할 수 없다. 이 한계와 별도 브로커 도입 기준은 제안 상태의 `ADR-004`에 기록하고 사용자 승인 시 확정한다.

### 3.3 클라이언트 식별자

인증 체계 도입 전에는 허용 목록 헤더 `X-Client-Id`를 임시 식별자로 사용한다. 값이 없거나 형식이 잘못되면 `anonymous`로 기록한다. 이 헤더는 신뢰할 수 있는 인증 수단이 아니므로 접근 권한 판정에 사용하지 않으며, 인증 도입 후 Security Principal 또는 검증된 client claim으로 교체한다.

### 3.4 추가 전용 정책

Application 코드에는 감사 로그 수정 메서드를 제공하지 않는다. Repository도 `save`, 검색, 보존 만료 삭제만 노출한다. 보존 삭제는 스케줄러 전용 서비스에서만 수행하고 삭제 건수·기준 시각을 별도 운영 로그로 남긴다. DB 계정과 권한 분리는 배포 환경 과제로 문서화한다.

## 4. 데이터 모델과 DDL 변경

`audit_log` 테이블을 추가한다.

| 컬럼 | 타입 | 제약 | 의미 |
| --- | --- | --- | --- |
| `audit_log_id` | BIGINT | PK, auto increment | 감사 로그 식별자 |
| `trace_id` | VARCHAR(64) | NOT NULL | 요청 추적 식별자 |
| `client_id` | VARCHAR(100) | NOT NULL | 검증·정규화된 클라이언트 식별자 |
| `http_method` | VARCHAR(10) | NOT NULL | HTTP 메서드 |
| `request_path` | VARCHAR(255) | NOT NULL | 템플릿 기반 정규화 경로 |
| `response_status` | INTEGER | NOT NULL | 최종 HTTP 상태 코드 |
| `error_code` | VARCHAR(64) | NULL | 공개 가능한 표준 오류 코드 |
| `success` | BOOLEAN | NOT NULL | 400 미만 여부 |
| `duration_ms` | BIGINT | NOT NULL | 처리 시간 |
| `requested_at` | TIMESTAMP(6) | NOT NULL | 요청 시작 시각 |
| `completed_at` | TIMESTAMP(6) | NOT NULL | 처리 완료 시각 |

모든 컬럼 comment는 프로젝트 DDL 규칙에 따라 `CREATE TABLE` 내부에 작성한다. 검색 패턴을 기준으로 다음 인덱스를 추가한다.

- `(requested_at DESC, audit_log_id DESC)`
- `(client_id, requested_at DESC)`
- `(request_path, requested_at DESC)`
- `(trace_id)`
- `(response_status, requested_at DESC)`

IP 주소, User-Agent, 쿼리 문자열 및 요청·응답 body는 1페이즈 저장 대상에서 제외한다.

## 5. 패키지 및 코드 파일 계획

현재 역할 우선 구조를 유지하되 향후 도메인 우선 패키지 이관 시 `audit` 경계를 그대로 이동할 수 있게 구성한다.

### 5.1 Domain

- `domain/entity/audit/AuditLog.java`
  - 감사 로그 필드와 생성 정적 팩토리를 제공한다.
  - setter와 업무 수정 메서드를 제공하지 않는다.
  - `durationMs >= 0`, 필수 문자열 길이, 시작·완료 시각 순서를 검증한다.
- `domain/exception/DomainErrorCode.java`
  - 필요한 경우 `INVALID_AUDIT_LOG`를 추가한다.

### 5.2 Application

- `application/dto/audit/AuditLogCommand.java`
  - Filter에서 수집한 허용 목록 값만 전달한다.
- `application/dto/audit/AuditLogSearchCondition.java`
  - 기간, clientId, path, status, traceId, 1-based page/size를 전달한다.
- `application/dto/audit/AuditLogResult.java`
  - 운영 조회에 필요한 안전한 필드만 반환한다.
- `application/service/audit/AuditLogService.java`
  - `record(command)`를 `REQUIRES_NEW`로 저장한다.
  - `search(condition)`과 `get(id)`를 읽기 전용 트랜잭션으로 제공한다.
- `application/exception/ApplicationErrorCode.java`
  - `AUDIT_LOG_NOT_FOUND`, `INVALID_AUDIT_SEARCH_CONDITION`을 추가한다.

### 5.3 Infrastructure

- `infrastructure/repository/audit/AuditLogRepository.java`
  - 추가 저장, Specification 검색 및 단건 조회만 노출하며 삭제 기능은 제공하지 않는다.
- `infrastructure/repository/audit/AuditLogSpecifications.java`
  - 선택 검색 조건을 조합한다.
- `src/main/resources/schema.sql`
  - 내부 column comment와 검색 인덱스를 포함한 `audit_log` DDL을 추가한다.

### 5.4 Presentation

- `presentation/audit/AuditLogFilter.java`
  - 요청 전후 메타데이터를 수집하고 저장 서비스를 호출한다.
  - `/swagger-ui/**`, `/v3/api-docs/**`, 정적 자원은 기본 제외하며 설정으로 조정한다.
- `presentation/audit/TraceIdFilter.java`
  - 유효한 `X-Trace-Id`를 이어받거나 새 UUID를 생성하고 응답 헤더와 MDC에 설정한 뒤 반드시 정리한다.
- `presentation/audit/AuditValueSanitizer.java`
  - clientId·traceId 길이와 허용 문자를 검사하고 경로를 정규화한다.
- `presentation/audit/AuditErrorCodeResolver.java`
  - 표준 `ApiResponse.code`를 body 재파싱 없이 request attribute에서 얻도록 예외 처리기와 연결한다.
- `presentation/audit/dto/AuditLogSearchRequest.java`
  - 날짜, 상태, 페이지 범위를 Bean Validation으로 검증한다.
- `presentation/audit/dto/AuditLogResponse.java`
  - 감사 로그 조회 응답을 정의한다.
- `presentation/audit/AuditLogQueryController.java`
  - `GET /api/v1/ops/audit-logs`
  - `GET /api/v1/ops/audit-logs/{auditLogId}`
- `presentation/common/GlobalExceptionHandler.java`
  - 표준 오류 코드를 request attribute에 기록해 감사 Filter가 안전하게 참조하도록 보완한다.

## 6. 요청 처리 순서

1. `TraceIdFilter`가 추적 ID를 검증 또는 생성한다.
2. `AuditLogFilter`가 시작 시각, 메서드 및 임시 clientId를 수집한다.
3. Controller와 Application 유스케이스가 요청을 처리한다.
4. 전역 예외 처리기는 안전한 오류 코드와 HTTP 상태를 결정한다.
5. `AuditLogFilter`의 `finally`에서 템플릿 경로, 상태, 종료 시각과 오류 코드를 확정한다.
6. `AuditLogService.record`가 별도 트랜잭션으로 추가 저장한다.
7. 응답에 추적 ID를 반환하고 MDC를 정리한다.

비동기 dispatch와 오류 dispatch에서 같은 요청이 중복 기록되지 않도록 request attribute에 기록 완료 플래그를 둔다.

## 7. API 계약

### 7.1 목록 조회

`GET /api/v1/ops/audit-logs`

- 선택 조건: `startDate`, `endDate`, `clientId`, `requestPath`, `responseStatus`, `traceId`
- 페이지: `page=1`, `size=20`, 최대 100
- 정렬: `requestedAt DESC, auditLogId DESC`
- 응답: `ApiResponse<PageResponse<AuditLogResponse>>`

### 7.2 단건 조회

`GET /api/v1/ops/audit-logs/{auditLogId}`

- 미존재 시 `AUDIT_LOG_NOT_FOUND`, HTTP 404
- 요청·응답 body, 헤더 원문 및 내부 예외 stack trace는 반환하지 않는다.

Swagger에는 검색 조건, 페이지 제한, 응답 모델과 400·404·500 오류를 명시한다. 인증 구현 전 운영 API의 접근 통제가 미완성임을 API 설명과 위험 항목에 표시한다.

## 8. 보안 및 개인정보 기준

- 수집 필드는 코드의 허용 목록으로 고정한다.
- `Authorization`, `Cookie`, `Set-Cookie`, `Idempotency-Key`는 읽거나 저장하지 않는다.
- 쿼리 문자열과 path variable 실제 값 대신 가능한 경우 URI 템플릿을 저장한다.
- 오류 메시지와 stack trace 대신 enum 오류 코드만 저장한다.
- `clientId`, `traceId`는 최대 길이와 허용 문자 검증 후 저장한다.
- 감사 조회 호출도 감사 로그에 기록하되 조회 결과 자체는 기록하지 않는다.
- 대량 반출 방지를 위한 인증·인가와 다운로드 제한은 보안 계층 구현 전 필수 후속 사항으로 관리한다.

## 9. 테스트 계획

### 9.1 단위 테스트

- `AuditLogTest`: 필수 값, 길이, 시각 순서, duration 검증
- `AuditValueSanitizerTest`: 허용 문자, 길이 제한, anonymous 대체, 경로 정규화
- `AuditLogServiceTest`: 저장·검색·미존재·페이지 검증
- `AuditErrorCodeResolverTest`: 성공·업무 오류·예상외 오류 코드 처리

### 9.2 필터·Controller 테스트

- 2xx, 4xx, 5xx 요청이 각각 한 번 기록되는지 검증
- 존재하지 않는 경로와 JSON 파싱 실패도 기록되는지 검증
- async/error dispatch에서 중복 기록되지 않는지 검증
- 추적 ID 생성·전파·MDC 정리 검증
- 감사 대상 제외 경로 검증
- 목록 검색, 단건 404, 페이지 검증과 OpenAPI 게시 검증

### 9.3 통합 테스트

- 업무 트랜잭션 롤백 후 감사 로그가 남는지 검증
- 감사 저장 실패가 완료된 업무 원장을 롤백하지 않는지 검증
- 실제 H2 schema에서 인덱스·컬럼 제약과 Repository 조건 조합 검증
- 민감 헤더·body·path variable 값이 DB에 존재하지 않는지 검증

### 9.4 최종 성능 검증으로 이관할 항목

- 감사 저장 전후 API p95·p99와 TPS 비교
- 감사 테이블 인덱스 쓰기 비용과 DB 커넥션 사용량
- 보존 삭제와 조회·업무 쓰기 경합
- 감사 저장 장애 시 실패 지표와 정상 회복

공식 판정은 모든 개발 완료 후 합의된 최종 부하 테스트에서 수행한다.

## 11. 완료 기준

- 성공·실패·바인딩 실패·미매핑 요청마다 감사 로그가 정확히 한 건 생성된다.
- 업무 트랜잭션 롤백과 독립적으로 감사 로그가 저장된다.
- 요청·응답 본문, 인증정보, 멱등키 및 개인정보가 저장되지 않는다.
- 기간·클라이언트·경로·상태·추적 ID 검색과 단건 조회가 동작한다.
- 감사 저장 실패가 탐지 가능하며 업무 원장의 완료 결과를 변경하지 않는다.
- OpenAPI, 단위·통합·HTTP 테스트와 기존 회귀 테스트가 통과한다.
- JaCoCo HTML 리포트가 생성된다.

## 12. 승인 요청 사항

1. 인메모리 비동기 큐 대신 `REQUIRES_NEW` 동기 저장을 1페이즈 기준으로 사용
2. 감사 저장 실패가 완료된 업무 요청을 실패로 바꾸지 않고 비상 로그·지표로 탐지
3. 인증 도입 전 `X-Client-Id`를 비신뢰 임시 식별자로 저장하고 접근 통제에는 사용하지 않음
4. 요청·응답 body, 쿼리 문자열, IP 및 User-Agent를 저장 대상에서 제외
5. Swagger·정적 자원은 기본 감사 대상에서 제외
6. 감사 로그 삭제 API·자동 삭제·보존 만료 삭제는 구현 범위에서 제외

## 13. 구현 결과

- `audit_log` Flyway DDL, 검색 인덱스와 추가 전용 JPA Entity·Repository를 구현했다.
- 추적 ID 전파, URI 템플릿 정규화, 성공·실패 요청 감사 Filter와 저장 실패 카운터를 구현했다.
- 감사 저장은 업무 트랜잭션과 분리된 `REQUIRES_NEW`를 적용했다.
- 운영 감사 목록·단건 조회 API와 OpenAPI 계약을 구현했다.
- 요청·응답 body, 인증정보, 멱등키, 쿼리 문자열과 미매핑 실제 경로는 저장하지 않는다.
- 사용자 결정에 따라 삭제 API, 자동 삭제, 보존 만료 삭제와 관련 Scheduler·Repository 기능은 구현하지 않았다.
- 단위·필터·통합·OpenAPI 테스트와 전체 회귀 테스트 및 JaCoCo 리포트 생성을 완료했다.
