## 2. 목표와 책임 경계

Application 레이어는 다음 유스케이스와 처리 흐름을 책임진다.

- 고객 지갑 생성·조회·충전
- 결제 PENDING 원장과 INIT 아웃박스의 원자적 생성
- 결제 생성 트랜잭션 커밋 이후 외부 PG 승인 처리
- PG 승인 결과에 따른 지갑 차감, 거래 이력 및 결제 상태의 원자적 반영
- 전액·부분 취소 원장 생성과 외부 PG 취소 후 지갑 환불
- 글로벌 멱등키 선점, 동일 요청 재조회 및 충돌 판정
- 고객용·운영자용 결제 이력 조회와 페이징·검색
- PG 응답 원문 암호화 및 로그 원장 저장
- 고립 아웃박스 이벤트 재처리
- 도메인·인프라 예외를 업무 오류로 분류

다음 책임은 제외한다.

- HTTP 요청 매핑, Bean Validation, `ApiResponse<T>` 직렬화 및 HTTP 상태 결정
- Swagger/OpenAPI Controller 어노테이션
- 실제 PG HTTP 통신과 암호화 알고리즘 구현
- 전체 시스템 부하 테스트 실행
- 프로젝트 완료 후 작성할 사용자 직접 테스트 케이스와 실행 안내서

## 3. 핵심 설계 원칙

- 외부 PG 호출 중에는 DB 트랜잭션, 비관적 잠금 및 DB 커넥션을 보유하지 않는다.
- 결제·취소 원장과 아웃박스는 외부 호출 전에 같은 트랜잭션으로 커밋한다.
- `@TransactionalEventListener(AFTER_COMMIT)`는 1페이즈에서 동기 실행하여 HTTP 요청이 최종 결제 결과를 조회할 수 있게 한다. `@Async`는 적용하지 않는다.
- PG 결과 반영은 별도 Spring Bean의 새 `@Transactional` 메서드에서 수행하여 self-invocation 문제를 방지한다.
- 지갑 변경은 지갑 비관적 잠금과 거래 이력 저장을 항상 같은 트랜잭션으로 묶는다.
- 취소 완료는 원 결제 잠금 후 지갑 잠금 순서를 일관되게 적용한다.
- 멱등키 선점과 업무 원장·리소스 연결은 같은 트랜잭션으로 저장하여 리소스 없는 멱등키가 커밋되지 않게 한다.
- 같은 멱등키의 동시 INSERT 충돌은 트랜잭션 밖 Facade에서 기존 결과 재조회로 처리한다.
- Application DTO는 HTTP 타입을 알지 않으며 Presentation DTO와 분리한다.
- 클래스와 공개 메서드에는 책임, 트랜잭션 경계 및 주요 제약을 설명하는 간결한 Javadoc을 작성한다.

## 4. 인프라 계약 위치 보정

현재 인프라 구현의 일부 인터페이스가 Infrastructure 패키지에 정의되어 있다. Application 구현 시 의존성 방향을 명확히 하기 위해 교체 가능한 계약을 Application 포트로 이동한다.

| 현재 계약 | 이동 위치 | Infrastructure 후속 변경 |
| --- | --- | --- |
| `infrastructure.pg.PgClient` 및 요청·응답 계약 | `application.port.out.pg` | `FakePgClient`가 Application 출력 포트를 구현 |
| `infrastructure.security.PayloadEncryptor` | `application.port.out.security` | `AesGcmPayloadEncryptor`가 Application 출력 포트를 구현 |
| `infrastructure.outbox.OutboxRecoveryPort` | `application.port.in.outbox` | `OutboxScheduler`가 Application 입력 포트에 의존 |

`PgScenario`와 Fake PG 설정은 인프라 테스트·개발 시뮬레이션 책임이므로 Infrastructure에 유지한다. Application의 PG 요청 계약에는 시나리오를 넣지 않고 Fake 구현이 설정 또는 테스트 대체 Bean으로 결과를 선택한다. 이 변경은 업무 로직 변경이 아니라 Clean Architecture 의존성 방향 보정이며 아키텍처 문서에 반영한다.

Spring Data Repository는 승인된 Layered Architecture에 따라 Infrastructure 패키지에 유지하고 Application Service가 주입받아 사용한다. 향후 다른 저장 기술 교체가 필요해지면 별도 Repository 출력 포트를 도입한다.

## 5. 패키지 및 파일 구성

기준 패키지는 `com.example.paymentsystem`으로 하며, 레이어 경계를 유지하면서 협업자가 역할을 먼저 식별할 수 있도록 아래 규칙을 적용한다.

- JPA 엔티티와 도메인 열거형: `domain.entity.<도메인>`
- Application 입출력 DTO: `application.dto.<도메인>`
- Application 서비스: `application.service.<도메인>`
- 공통 계산 유틸리티: `application.util`
- Spring Data Repository: `infrastructure.repository.<도메인>`
- 포트·이벤트·예외·외부 어댑터는 각각 `port`, `event`, `exception`, Infrastructure 기술 패키지에 유지한다.

```text
application/
├─ dto/{wallet,payment,cancel,query,outbox}/
├─ service/{customer,wallet,payment,cancel,query,outbox,idempotency}/
├─ util/
├─ port/
│  ├─ in/
│  │  └─ outbox/
│  │     └─ OutboxRecoveryUseCase.java
│  └─ out/
│     ├─ pg/
│     │  ├─ PgClient.java
│     │  ├─ PgApprovalCommand.java
│     │  ├─ PgApprovalResult.java
│     │  ├─ PgCancelCommand.java
│     │  └─ PgCancelResult.java
│     └─ security/
│        └─ PayloadEncryptor.java
├─ event/
│  ├─ PaymentCreatedEvent.java
│  ├─ PaymentCancelCreatedEvent.java
│  ├─ PaymentEventListener.java
│  └─ PaymentCancelEventListener.java
└─ exception/
   ├─ ApplicationErrorCode.java
   └─ ApplicationException.java
```

기존 Infrastructure 변경:

```text
infrastructure/
├─ pg/FakePgClient.java
├─ security/AesGcmPayloadEncryptor.java
├─ outbox/OutboxScheduler.java
└─ repository/payment/PaymentSpecifications.java
```

도메인 변경:

```text
domain/entity/outbox/OutboxEventType.java
  - PAYMENT_CANCEL_REQUESTED 추가
```

취소도 외부 PG 호출 전 PENDING 원장을 커밋하고 JVM 장애 시 복구할 수 있어야 하므로 기존 `payment_outbox`를 재사용한다. payload에 `cancelId`를 포함하며 별도 취소 아웃박스 테이블은 만들지 않는다.

## 6. 공통 Application 오류 모델

`ApplicationErrorCode`는 Application에서 직접 판정하는 다음 오류를 정의한다.

| 코드 | 발생 조건 |
| --- | --- |
| `CUSTOMER_NOT_FOUND` | 지갑 생성 대상 고객이 없음 |
| `WALLET_NOT_FOUND` | 지갑 조회·충전·결제·환불 대상 없음 |
| `DUPLICATE_WALLET` | 고객에게 이미 지갑이 존재함 |
| `PAYMENT_NOT_FOUND` | 결제 조회·취소 대상 없음 |
| `IDEMPOTENCY_CONFLICT` | 동일 멱등키의 요청 유형 또는 지문이 다름 |
| `INVALID_CANCEL_AMOUNT` | 취소 유형과 금액 또는 잔여 한도 불일치 |
| `SYSTEM_ERROR` | PG 기술 오류, 암호화·DB·예상하지 못한 내부 오류 |

- `ApplicationException`은 오류 enum과 필요한 추적 식별자만 보유한다.
- HTTP 상태와 응답 메시지 노출 범위는 Presentation의 예외 처리기가 결정한다.
- `DomainException`, `PgClientException`, `EncryptionException`, 락 타임아웃 및 DB 예외의 변환표를 테스트한다.
- 로그에는 paymentId, cancelId, outboxId 같은 추적 ID만 포함하고 PG 원문·키·개인정보를 포함하지 않는다.

## 7. 글로벌 멱등성 처리

### 7.1 요청 지문

`IdempotencyFingerprintGenerator`는 UTF-8 정규화 문자열을 SHA-256 소문자 hex로 변환한다.

| 요청 유형 | 정규화 대상 |
| --- | --- |
| 결제 | `PAYMENT|customerId|amount` |
| 충전 | `WALLET_TOP_UP|customerId|amount` |
| 취소 | `PAYMENT_CANCEL|paymentId|cancelType|amount` |

- 구분자 충돌을 막기 위해 각 값의 공백·대소문자 정책을 명시하고 enum은 `name()`을 사용한다.
- 멱등키 자체, 이메일, PG 원문 및 암호화 키는 지문 원문에 포함하지 않는다.

### 7.2 최초 요청

1. 업무별 생성 Service의 동일 트랜잭션에서 `IdempotencyRecord.reserve`를 INSERT한다.
2. 결제·취소·지갑 거래 원장을 생성한다.
3. 생성된 리소스 ID를 `linkResource`로 연결한다.
4. 결제·취소는 같은 트랜잭션에서 INIT 아웃박스를 생성한다.
5. 트랜잭션 커밋 시점까지 하나라도 실패하면 전부 롤백한다.

### 7.3 중복·충돌 요청

- Facade는 최초 생성 Service의 UNIQUE 위반을 잡고 별도 읽기 Service로 글로벌 멱등성 원장을 다시 조회한다.
- 요청 유형과 지문이 같으면 `resourceId`로 기존 결과를 조회하여 반환한다.
- 유형 또는 지문이 다르면 `IDEMPOTENCY_CONFLICT`를 발생시킨다.
- DB 고유성 제약이 최종 방어선이므로 사전 `exists` 조회만으로 중복 여부를 결정하지 않는다.

## 8. 지갑 유스케이스

### 8.1 지갑 생성

`WalletService.createWallet(customerId)`:

- Customer 존재 여부를 확인한다.
- 기존 Wallet이 있으면 `DUPLICATE_WALLET`을 발생시킨다.
- 초기 잔액 0원의 Wallet을 저장한다.
- DB UNIQUE 경합도 `DUPLICATE_WALLET`으로 변환한다.

### 8.2 잔액 조회

- 일반 조회 Repository를 사용하며 쓰기 잠금을 획득하지 않는다.
- 지갑이 없으면 `WALLET_NOT_FOUND`를 발생시킨다.

### 8.3 멱등 충전

`WalletService.topUp(WalletCommand.TopUp)`:

1. 글로벌 멱등키를 선점한다.
2. 고객 지갑을 `findByCustomerIdWithLock`으로 조회한다.
3. `Wallet.increase`로 잔액을 증가시킨다.
4. 변경 후 잔액으로 TOP_UP `WalletTransaction`을 저장한다.
5. 멱등 레코드에 거래 ID를 연결한다.

위 작업은 하나의 트랜잭션이며 중복 요청은 기존 거래와 현재 잔액 결과를 반환한다.

## 9. 결제 유스케이스와 트랜잭션 경계

### 9.1 결제 요청 Facade

`PaymentFacade.requestPayment(PaymentCommand.Create)`는 트랜잭션을 직접 보유하지 않는다.

1. `PaymentCreationService.createPending` 호출
2. 멱등 UNIQUE 충돌이면 기존 Payment 결과 판정
3. 생성 Service 반환 후 `PaymentResultService`로 최종 상태 재조회
4. Presentation에 전달할 `PaymentResult` 반환

### 9.2 PENDING 원장 생성 트랜잭션

`PaymentCreationService.createPending` (`@Transactional`):

1. 고객·지갑 존재 여부 확인
2. 글로벌 결제 멱등키 INSERT
3. `Payment.createPending` 저장 및 ID 확보
4. `PaymentOutbox.createPaymentRequested`를 INIT으로 저장
5. 멱등 레코드에 paymentId 연결
6. `PaymentCreatedEvent(paymentId, outboxId)` 발행
7. Payment·Outbox·IdempotencyRecord 원자적 커밋

### 9.3 커밋 후 PG 호출

`PaymentEventListener.handle`:

- `@TransactionalEventListener(phase = AFTER_COMMIT)`을 사용한다.
- `@Async`를 사용하지 않아 1페이즈 요청이 최종 결과를 기다릴 수 있게 한다.
- Listener 자체에는 `@Transactional`을 적용하지 않는다.
- `PgClient.approve` 호출 시 결제 멱등키를 외부 멱등키로 전달한다.
- 승인·거절 응답은 암호화 후 결과 반영 Service에 전달한다.
- 오류·타임아웃은 `SYSTEM_ERROR` 결과 반영 Service로 전달한다.

### 9.4 PG 결과 반영 트랜잭션

`PaymentProcessingService`는 Listener와 다른 Spring Bean이며 각 메서드가 새 트랜잭션을 시작한다.

#### 승인

1. Payment 재조회 및 PENDING 확인
2. 고객 Wallet 비관적 잠금 획득
3. 잔액 충분 시 차감 및 PAYMENT WalletTransaction 저장
4. Payment `COMPLETED` 전환
5. 암호화된 PgResponseLog 저장
6. Outbox `PUBLISHED` 전환

#### 승인 후 잔액 부족

- Wallet 잔액과 거래 이력은 변경하지 않는다.
- Payment를 `FAILED/INSUFFICIENT_BALANCE`로 전환한다.
- PG 로그 저장 및 Outbox를 `PUBLISHED`로 전환한다.

#### PG 거절

- Payment를 `FAILED/EXTERNAL_PAYMENT_REJECTED`로 전환한다.
- 암호화 PG 로그 저장 및 Outbox를 `PUBLISHED`로 전환한다.

#### PG 오류·타임아웃

- Payment를 `FAILED/SYSTEM_ERROR`로 전환한다.
- 응답 원문이 없으면 PgResponseLog를 생성하지 않는다.
- 업무 처리가 최종 실패로 완료됐으므로 Outbox를 `PUBLISHED`로 전환한다.

#### 내부 DB 반영 실패

- 결과 반영 트랜잭션 전체를 롤백하여 Payment PENDING과 Outbox INIT을 유지한다.
- 스케줄러가 이후 같은 멱등키로 PG를 재호출한다.

## 10. 결제 취소 유스케이스

### 10.1 취소 원장 생성

`PaymentCancelCreationService.createPending` (`@Transactional`):

1. 글로벌 취소 멱등키 선점
2. Payment 비관적 잠금 획득
3. 취소 가능 상태와 남은 금액 확인
4. FULL은 남은 금액 전체, PARTIAL은 남은 금액 미만인지 검증
5. PENDING PaymentCancel 저장
6. `PAYMENT_CANCEL_REQUESTED` Outbox 저장
7. 멱등 레코드에 cancelId 연결
8. `PaymentCancelCreatedEvent(paymentId, cancelId, outboxId)` 발행 후 원자적 커밋

### 10.2 커밋 후 외부 취소

- `PaymentCancelEventListener`가 `AFTER_COMMIT`에 PG 취소를 호출한다.
- 승인 결과와 원문은 처리 Service로 전달하며 외부 호출 중 DB 트랜잭션을 보유하지 않는다.

### 10.3 취소 결과 반영

`PaymentCancelProcessingService` (`@Transactional`):

#### 승인

1. Payment 비관적 잠금
2. PaymentCancel PENDING 재확인
3. Wallet 비관적 잠금
4. 환불 금액 증가 및 REFUND WalletTransaction 저장
5. Payment 누적 취소 금액과 상태 갱신
6. PaymentCancel COMPLETED 전환
7. 암호화 PG 로그 저장
8. Outbox PUBLISHED 전환

#### 거절·오류·타임아웃

- 원 Payment와 Wallet은 변경하지 않는다.
- PaymentCancel만 FAILED와 실패 사유로 전환한다.
- 정상 거절 응답은 암호화 로그로 저장한다.
- Outbox는 최종 처리 완료 의미로 PUBLISHED 전환한다.

## 11. 조회 유스케이스

### 11.1 고객 조회

- `customerId`와 Payment 소유자를 Repository 조건으로 함께 검증한다.
- 고객 목록은 1-based 요청을 0-based `PageRequest`로 변환한다.
- 기본 20건, 최대 100건, `createdAt DESC`를 적용한다.
- 상태, 금액, 실패 사유, 취소 이력만 반환하고 PG 로그·암호문·내부 Outbox를 노출하지 않는다.

### 11.2 운영자 조회

- `PaymentSpecifications`로 paymentId, customerId, status, failureReason, startDate, endDate 조건을 조합한다.
- 단건 상세에 취소 이력, 지갑 거래 참조, PG 응답 메타데이터와 로그 ID를 포함한다.
- 암호화 payload 자체와 암호화 키는 반환하지 않는다.
- 날짜 범위 역전, page 0 이하, size 100 초과는 Application 오류로 처리한다.

### 11.3 PageResult

- `content`, 1-based `page`, `size`, `totalElements`, `totalPages`를 제공한다.
- Spring Data `Page`를 Presentation에 직접 노출하지 않는다.

## 12. 아웃박스 복구

`OutboxRecoveryService`는 `OutboxRecoveryUseCase`를 구현한다.

1. 전달받은 outboxId로 이벤트 메타데이터를 조회한다.
2. PUBLISHED 또는 FAILED이면 중복 처리 없이 종료한다.
3. eventType과 payload의 paymentId·cancelId를 검증한다.
4. 결제 생성 이벤트는 Payment 처리 흐름, 취소 이벤트는 Cancel 처리 흐름으로 전달한다.
5. 외부 PG 호출은 트랜잭션 밖에서 수행한다.
6. 결과 반영은 기존 Processing Service의 독립 트랜잭션을 재사용한다.
7. 실패 시 별도 트랜잭션으로 `recordFailure`, 최대 횟수 도달 시 `markFailed`를 호출한다.

- payload JSON 직렬화·역직렬화 전용 DTO를 사용한다.
- 이벤트 ID, paymentId, cancelId 불일치는 `SYSTEM_ERROR`로 기록하고 외부 호출하지 않는다.
- 1페이즈 단일 스케줄러와 PG 멱등키를 전제로 중복 외부 호출의 부작용을 차단한다.

## 14. 테스트 계획

### 14.1 Service 단위 테스트

- 지갑 생성·중복·미존재 고객·잔액 조회
- 충전 최초 요청·동일 재요청·멱등 충돌·잔액 overflow
- 결제 PENDING 생성 시 Payment·Outbox·멱등 레코드 저장과 이벤트 발행
- PG 승인·잔액 부족·거절·오류·타임아웃 상태 매핑
- 부분·전액·반복 취소와 취소 실패 시 원 결제 불변
- 고객 소유권과 운영 검색 조건·페이지 경계
- 도메인·인프라 예외의 Application 오류 변환

### 14.2 트랜잭션 통합 테스트

- Payment·Outbox·IdempotencyRecord 중 하나 실패 시 전체 롤백
- PENDING 커밋 전 PG 호출이 발생하지 않음
- AFTER_COMMIT 시 PG 호출 시점에 원장이 다른 트랜잭션에서 조회됨
- PG 호출 동안 DB 커넥션·지갑 잠금을 보유하지 않음
- 승인 후 Wallet·WalletTransaction·Payment가 모두 반영되거나 모두 롤백
- 취소 후 Wallet·Refund Transaction·PaymentCancel·Payment가 모두 반영되거나 모두 롤백
- 내부 결과 반영 실패 시 Outbox INIT 유지 및 복구 재처리 성공

### 14.3 멱등성·동시성 테스트

- 같은 결제 요청 30개 동시 실행 시 Payment와 PG 처리가 한 건만 생성됨
- 동일 키·다른 고객 또는 금액은 모두 `IDEMPOTENCY_CONFLICT`
- 동일 지갑 동시 결제에서 음수 잔액과 초과 차감 0건
- 동일 결제 동시 부분 취소에서 누적 취소액 초과 0건
- 충전·결제·취소 간 같은 글로벌 키 사용 시 한 업무만 성공

### 14.4 이벤트·복구 테스트

- 원장 저장 롤백 시 AFTER_COMMIT Listener 미호출
- 정상 처리 시 Outbox PUBLISHED
- JVM 이벤트 유실을 가정한 INIT 이벤트 재처리
- 일부 복구 실패가 다른 이벤트 처리를 막지 않음
- 재시도 한도 도달 시 FAILED
- 이미 PUBLISHED 이벤트의 중복 복구 무시

### 14.5 조회 테스트

- 1-based 페이지 변환, 기본 20·최대 100, 생성일 내림차순
- 고객 정보 은닉과 소유권 검증
- 운영자 복합 조건 검색과 날짜 경계
- PG 암호문 및 Outbox payload 응답 제외

### 14.6 전체 검증

- `gradlew.bat clean test jacocoTestReport`
- 기존 도메인·인프라 테스트 회귀 없음
- JaCoCo HTML/XML 리포트 생성
- 전체 시스템 부하 테스트와 사용자 직접 테스트 문서 작성은 수행하지 않음

## 17. 승인 시 함께 확정할 사항

1. 1페이즈 `AFTER_COMMIT` Listener는 동기로 실행하고 API가 최종 결과를 재조회하여 반환한다.
2. 취소 요청도 기존 `payment_outbox`를 재사용해 JVM 장애 복구 대상으로 포함한다.
3. 교체 가능한 PG·암호화·복구 계약을 Application 포트로 이동한다.
4. PG 오류·타임아웃은 요구사항대로 즉시 최종 `FAILED/SYSTEM_ERROR` 처리하고 Outbox는 PUBLISHED로 종료한다.
5. 내부 DB 결과 반영 실패만 Outbox INIT으로 남겨 재시도한다.
