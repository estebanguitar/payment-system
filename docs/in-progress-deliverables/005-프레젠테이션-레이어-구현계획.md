## 2. 목표와 책임 경계

Presentation 레이어는 다음 책임만 가진다.

- HTTP Header, Path, Query, JSON Body를 Presentation 요청 DTO로 역직렬화한다.
- Bean Validation으로 형식·필수값·기본적인 값 범위를 검증한다.
- Presentation 요청 DTO를 Application Command 또는 검색 조건으로 변환한다.
- Application 결과를 공개 API 응답 DTO와 `ApiResponse<T>`로 변환한다.
- Application·Domain·입력 검증 예외를 표준 오류 코드와 HTTP 상태로 매핑한다.
- 고객용 API와 운영자용 API를 구분하고 OpenAPI 3 명세와 Swagger UI를 제공한다.
- Controller, 예외 처리기, DTO 변환 및 실제 HTTP 계약을 자동화 테스트로 검증한다.

다음 책임은 포함하지 않는다.

- 결제·취소·지갑의 업무 규칙 또는 트랜잭션 처리
- Repository 직접 접근과 엔티티 반환
- PG 호출, 암호화 및 아웃박스 복구
- 인증·인가와 운영자 권한 검증
- 최종 부하 테스트와 사용자 직접 테스트 안내서 작성
- 개발 완료 후 수행할 도메인 우선 패키지 구조 개선

## 3. 설계 원칙

- Controller는 Application Service만 호출하며 Domain Entity와 Repository를 알지 않는다.
- Presentation DTO와 Application DTO를 분리하고 각 요청 DTO에 `toCommand` 또는 `toCondition` 변환 메서드를 둔다.
- 응답 DTO는 Application 결과를 `from` 정적 팩토리로 변환하며 내부 멱등키, 암호문, Outbox payload를 노출하지 않는다.
- Controller에는 트랜잭션을 선언하지 않는다.
- 업무 실패를 HTTP 200으로 감싸지 않고 오류 성격에 맞는 4xx·5xx 상태를 사용한다.
- 예상하지 못한 예외 메시지와 stack trace는 외부 응답에 노출하지 않는다.
- 각 클래스에는 책임, 각 공개 메서드에는 기능과 주요 제약을 설명하는 간결한 주석을 작성한다.
- API 경로는 기존 `/api/v1` 명세를 유지한다.

## 4. 의존성 및 설정 변경

### 4.1 Gradle

`build.gradle`에 Spring Boot 3.5.x 호환 공식 starter를 추가한다.

```groovy
implementation 'org.springdoc:springdoc-openapi-starter-webmvc-ui:2.8.17'
```

Springdoc 공식 호환표상 Spring Boot 3.5.x는 2.8.x를 사용한다. 구현 시점에 2.8.x의 더 최신 안정 패치가 존재하면 변경 이유와 검증 결과를 문서화한 뒤 적용한다.

  swagger-ui:
    path: /swagger-ui.html
    operations-sorter: method
    tags-sorter: alpha

- 개발 환경에서 `/swagger-ui.html`, `/v3/api-docs`, `/v3/api-docs.yaml`을 제공한다.
- 인증·인가가 제외 범위임을 OpenAPI description에 명시한다.
- Actuator와 H2 Console은 공개 업무 API 명세 그룹에서 제외한다.

## 6. 공통 응답 모델

### 6.1 ApiResponse<T>

```json
{
  "code": "OK",
  "message": "정상적으로 처리되었습니다.",
  "returnObject": {}
}
```

- `success(message, data)`와 `error(code, message, detail)` 정적 팩토리를 제공한다.
- 성공 응답의 `code`는 `OK`로 통일한다.
- 오류 응답도 같은 최상위 필드를 유지하고 필요한 경우 `returnObject`에 안전한 `ErrorDetail`을 담는다.
- 응답 모델은 불변 DTO로 작성하고 엔티티를 필드로 보유하지 않는다.

### 6.2 ErrorDetail

- Bean Validation 오류에 한해 `field`, `reason` 목록을 제공한다.
- 거절된 실제 값, stack trace, 클래스명, SQL 및 내부 예외 메시지는 포함하지 않는다.
- 동일 필드 오류는 필드명 순으로 정렬하여 테스트 결과와 클라이언트 처리를 결정적으로 유지한다.

## 7. HTTP 오류 매핑

### 7.1 Application 오류

| 오류 코드 | HTTP 상태 |
| --- | --- |
| `CUSTOMER_NOT_FOUND` | 404 Not Found |
| `WALLET_NOT_FOUND` | 404 Not Found |
| `PAYMENT_NOT_FOUND` | 404 Not Found |
| `CANCEL_NOT_FOUND` | 404 Not Found |
| `DUPLICATE_WALLET` | 400 Bad Request |
| `IDEMPOTENCY_CONFLICT` | 409 Conflict |
| `INVALID_PAGE_REQUEST` | 400 Bad Request |
| `INVALID_DATE_RANGE` | 400 Bad Request |
| `SYSTEM_ERROR` | 500 Internal Server Error |

`DUPLICATE_WALLET`은 기존 아키텍처 오류표와의 호환성을 위해 400을 유지한다. 정책 변경이 필요하면 API 명세·아키텍처 문서와 함께 승인받는다.

### 7.2 Domain 및 HTTP 입력 오류

| 오류 코드·예외 | HTTP 상태 |
| --- | --- |
| `INVALID_REQUIRED_VALUE`, `INVALID_AMOUNT`, `INVALID_CANCEL_AMOUNT` | 400 Bad Request |
| `INSUFFICIENT_BALANCE` | 400 Bad Request |
| `INVALID_PAYMENT_STATE` | 409 Conflict |
| `OUTBOX_RETRY_OVERFLOW` | 500 Internal Server Error |
| `MethodArgumentNotValidException`, `ConstraintViolationException`, 타입 변환 실패 | 400 Bad Request |
| 필수 Header·Query·Path 누락 | 400 Bad Request |
| 지원하지 않는 HTTP Method | 405 Method Not Allowed |
| 읽을 수 없는 JSON 또는 enum 값 | 400 Bad Request |
| 그 밖의 예상하지 못한 예외 | 500 Internal Server Error / `SYSTEM_ERROR` |

`GlobalExceptionHandler`는 구체적인 예외부터 처리하며 예상하지 못한 예외만 서버 로그에 stack trace와 추적 ID를 남긴다. 멱등키와 PG 원문은 로그에 남기지 않는다.

## 8. 입력 검증 및 멱등키 정책

- `customerId`: `@NotBlank`, 최대 64자
- `Idempotency-Key`: `@RequestHeader`, `@NotBlank`, 최대 128자
- 금액: `@Positive`
- `paymentId`: `@Positive`
- `cancelType`: `@NotNull`, `FULL` 또는 `PARTIAL`
- `page`: 기본 1, 최소 1
- `size`: 기본 20, 최소 1, 최대 100
- 조회 날짜: ISO-8601 `LocalDateTime`, 시작·종료 역전은 Application에서 검증
- 공백만 있는 Header와 고객 ID는 유효하지 않은 요청으로 처리한다.
- Controller는 멱등키를 응답 또는 로그에 그대로 노출하지 않는다.

## 9. Controller별 구현계획

### 9.1 WalletController

| Method | 경로 | Application 호출 | 성공 상태 |
| --- | --- | --- | --- |
| POST | `/api/v1/wallets` | `WalletService.createWallet` | 200 OK |
| GET | `/api/v1/wallets/{customerId}` | `WalletService.getWallet` | 200 OK |
| POST | `/api/v1/wallets/{customerId}/top-up` | `WalletService.topUp` | 200 OK |

- 생성 요청은 `CreateWalletRequest.customerId`를 사용한다.
- 충전 요청의 customerId는 Path, amount는 Body, 멱등키는 Header에서 조합한다.
- 성공 메시지는 각각 `지갑이 생성되었습니다.`, `정상적으로 처리되었습니다.`, `충전이 완료되었습니다.`로 정의한다.

### 9.2 PaymentController

| Method | 경로 | Application 호출 | 성공 상태 |
| --- | --- | --- | --- |
| POST | `/api/v1/payments` | `PaymentFacade.requestPayment` | 200 OK |
| POST | `/api/v1/payments/{paymentId}/cancel` | `PaymentCancelFacade.cancel` | 200 OK |

- 결제 요청은 customerId와 amount Body에 멱등 Header를 결합해 `PaymentCommand`를 생성한다.
- 취소 요청은 paymentId Path, cancelType·amount Body, 멱등 Header를 결합한다.
- Application이 동기식 AFTER_COMMIT 처리 후 반환한 최종 상태를 그대로 응답한다.
- 업무적으로 실패한 결제 결과가 정상적인 요청 처리 결과로 반환되는 현재 Application 계약과, 예외 기반 HTTP 오류를 구분한다.

### 9.3 CustomerPaymentController

| Method | 경로 | Application 호출 |
| --- | --- | --- |
| GET | `/api/v1/customers/{customerId}/payments` | `PaymentQueryService.getCustomerPayments` |
| GET | `/api/v1/customers/{customerId}/payments/{paymentId}` | `PaymentQueryService.getCustomerPayment` |

- 기존 API 명세의 목록 API를 구현하고 단건 소유권 검증 API를 명시적으로 추가한다.
- 고객 응답에는 결제 상태·실패 사유·취소 이력만 포함하고 PG 로그 ID와 지갑 내부 참조 정보를 제외한다.

### 9.4 OperationsPaymentController

| Method | 경로 | Application 호출 |
| --- | --- | --- |
| GET | `/api/v1/ops/payments` | `PaymentQueryService.search` |
| GET | `/api/v1/ops/payments/{paymentId}` | `PaymentQueryService.getOperationsPayment` |

- 검색 Query를 `PaymentSearchRequest`로 바인딩하고 `PaymentSearchCondition`으로 변환한다.
- 운영 상세에는 취소 이력, 지갑 거래 참조, PG 응답 로그 ID를 포함한다.
- 암호화 payload와 복호화 결과는 반환하지 않는다.

## 10. Swagger/OpenAPI 구현

### 10.1 전역 설정

- `OpenAPI` Bean에 제목, 설명, 버전 및 개발 서버 정보를 정의한다.
- `GroupedOpenApi`로 `wallet`, `payment`, `customer-query`, `operations` 그룹을 구성하거나 동일 목적의 Tag 분리를 적용한다.
- 공개 API에 `@Tag`, `@Operation`, `@ApiResponse`, `@Parameter`를 작성한다.
- DTO 필드에 `@Schema`로 설명, 예시, 허용값 및 nullable 여부를 명시한다.

### 10.2 오류 문서화

- 각 API에 발생 가능한 400, 404, 409, 500 응답을 문서화한다.
- 공통 오류 Schema를 재사용하고 Controller별 가능한 업무 오류 코드를 description에 명시한다.
- `Idempotency-Key`는 필수 Header와 최대 길이, 동일 요청 재사용 정책을 문서화한다.

## 11. 테스트 계획

### 11.1 DTO 단위 테스트

- 모든 `toCommand`, `toCondition`, `from` 메서드의 필드 매핑
- PageResponse의 1-based 페이지 메타데이터
- 고객 응답에서 운영 정보가 제외되는지 검증
- 운영 응답에서 암호화 payload가 제외되는지 검증

### 11.2 Controller Slice 테스트

`@WebMvcTest`와 `MockMvc`, `@MockitoBean`을 사용한다.

- 각 Controller 공개 메서드의 Path·Query·Header·Body 매핑
- Application Service 호출 인자와 호출 횟수
- 정상 응답 HTTP 상태, 메시지와 JSON 필드
- 멱등 Header 누락·공백·길이 초과
- customerId·amount·cancelType·paymentId 검증
- page 기본값과 0 이하, size 100 초과
- 잘못된 enum·날짜·JSON 입력

### 11.3 예외 처리기 단위·Slice 테스트

- 모든 ApplicationErrorCode의 HTTP 상태와 응답 code·message
- 주요 DomainErrorCode의 HTTP 상태와 표준 메시지
- Bean Validation 필드 오류의 결정적 정렬
- 예상하지 못한 예외의 `SYSTEM_ERROR` 변환과 내부 메시지 비노출

### 11.4 OpenAPI 계약 통합 테스트

- `/v3/api-docs`와 `/swagger-ui.html` 접근 가능
- 모든 공개 경로와 HTTP Method 존재
- `Idempotency-Key` 필수 Header 표시
- 공통 성공·오류 Schema 존재
- 고객·운영자 응답의 민감·내부 필드 비노출

### 11.5 전체 인수 테스트

- API로 고객·지갑 생성과 멱등 충전
- 정상 결제, 잔액 부족, PG 거절·오류
- 전액·부분 취소와 멱등 재요청
- 고객 목록·단건 소유권 조회
- 운영 검색·상세 조회
- 실제 HTTP 결과와 Application·DB 상태의 정합성

전체 검증 명령은 `gradlew.bat clean test jacocoTestReport`이며 JaCoCo HTML/XML 리포트를 생성한다.

## 13. 완료 기준

- 명세된 지갑·결제·취소·고객 조회·운영 조회 API가 모두 호출된다.
- 모든 요청이 Bean Validation과 Application 검증을 통과해 안전하게 처리된다.
- 성공·오류가 `ApiResponse<T>` 구조와 합의된 HTTP 상태로 반환된다.
- Application·Domain·HTTP 입력·예상하지 못한 예외 매핑이 테스트된다.
- Controller가 Repository와 Domain Entity에 직접 의존하지 않는다.
- 고객 응답에 운영 정보, PG 원문 및 암호화 payload가 노출되지 않는다.
- Swagger UI와 OpenAPI JSON/YAML에서 전체 API, Header, DTO 및 오류 정책을 확인할 수 있다.
- Controller·DTO·예외 처리·OpenAPI 계약 테스트와 기존 테스트가 모두 통과한다.
- JaCoCo HTML/XML 리포트가 생성된다.
- 구현 결과와 요구사항·아키텍처·API 명세의 차이가 문서화된다.

3. 고객 결제 단건과 운영 결제 단건 API 추가
4. 인증·인가 없이 운영자 API를 논리적 경로와 응답 정보 수준으로만 구분
5. Swagger에서 암호문·PG 원문·멱등키 값은 예시를 포함해 실제 데이터로 노출하지 않음

## 15. 구현 결과

- 지갑 생성·조회·충전, 결제 생성·취소, 고객 결제 목록·상세, 운영 결제 검색·상세 Controller를 구현했다.
- HTTP 요청·응답 DTO를 Application DTO와 분리하고 Bean Validation 및 명시적 변환 메서드를 적용했다.
- `ApiResponse`, 필드 오류 상세, 계층별 예외 매핑과 OpenAPI 전역 설정을 구현했다.
- Springdoc Swagger UI와 `/v3/api-docs`를 활성화하고 핵심 경로 게시 계약을 자동 검증했다.
- Controller 전체 경로의 바인딩, 상태 코드, 공통 응답 및 입력 오류 테스트를 추가했다.
- `gradlew test jacocoTestReport`를 실행해 전체 테스트 통과와 JaCoCo HTML 리포트 생성을 확인했다.
- 후속 요청인 클라이언트 요청 감사 로그는 `AUD-001`, `AUD-002`로 요구사항을 확정했으며 저장소·비동기 적재·보존 정책은 별도 구현계획과 ADR 승인 대상으로 분리했다.
