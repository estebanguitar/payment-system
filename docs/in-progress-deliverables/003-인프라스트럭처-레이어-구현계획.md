## 2. 목표와 책임 경계

인프라스트럭처 레이어는 도메인 규칙을 새로 정의하지 않고 다음 기술 책임을 제공한다.

- Spring Data JPA 기반 원장 저장·조회와 DB 유일성 제약 연결
- 지갑 및 원 결제 Aggregate의 비관적 쓰기 잠금
- 시스템 전체에서 유일한 멱등키 선점·조회 저장소
- 승인·거절·오류·타임아웃을 결정적으로 재현하는 가상 PG Client
- 외부 PG 응답 원문의 AES-256-GCM 암호화·복호화
- 미발행 아웃박스 조회, 잠금 및 재시도 스케줄링 기반
- 설정값 바인딩과 인프라 예외의 기술적 분류

다음 책임은 이 단계에서 제외한다.

- 결제·취소·충전 유스케이스와 트랜잭션 오케스트레이션
- Controller, 요청·응답 DTO, Swagger 문서화
- `@TransactionalEventListener`가 호출할 결제 처리 Application Service
- 고객·운영자 조회 응답 조립 및 다이나믹 검색 조건 조합
- 실제 외부 PG HTTP 연동, 운영용 KMS·Vault, Kafka·CDC
- 전체 시스템 부하 테스트 실행 및 성능 결과 보고서 작성

부하 테스트는 인프라스트럭처 레이어 단독 완료 기준에 포함하지 않는다. 모든 계층의 개발과 기능·통합·인수 테스트가 완료된 뒤 최종 시스템 검증 단계에서 별도 구현계획과 실행 승인을 거쳐 수행한다. 이 단계에서는 향후 부하 테스트가 잠금 대기, 커넥션 풀 및 PG 지연을 측정할 수 있도록 Repository와 가상 PG의 결정적 테스트 기반만 제공한다.

## 3. 설계 원칙

- Domain 레이어는 Infrastructure 타입에 의존하지 않는다.
- Repository는 도메인 엔티티를 저장하되 업무 상태 전이를 수행하지 않는다.
- Repository를 공통 패키지에 모으지 않고 고객·지갑·결제·취소·PG 로그·아웃박스·멱등성 도메인별 영속성 패키지로 분리한다.
- 잠금은 Aggregate Root 조회에만 적용하고 외부 PG 호출 중에는 DB 트랜잭션과 잠금을 유지하지 않는다.
- 암호화 키, 평문 PG 응답 및 인증정보는 로그에 출력하지 않는다.
- 가상 PG 결과는 테스트가 시간·확률에 의존하지 않도록 명시적 시나리오로 결정한다.
- 인프라 예외는 기술 원인을 보존하고 Application 레이어가 업무 실패 사유로 변환할 수 있게 분류한다.
- 클래스와 공개 메서드에는 협업자가 책임과 제약을 파악할 수 있는 간결한 Javadoc을 작성한다.


`OutboxRecoveryPort`는 스케줄러가 Application 구현을 호출하기 위한 경계 인터페이스다. Application 레이어 구현 전에는 스케줄러를 기본 비활성화하여 불완전한 처리 흐름이 실행되지 않게 한다.

영속성 패키지는 도메인 경계를 기준으로 분리한다. 예를 들어 지갑과 지갑 거래 이력은 동일한 `persistence.wallet` 패키지에 두고, 결제 취소는 원 결제와 생명주기가 다르므로 `persistence.cancel`로 분리한다. PG 응답 로그와 아웃박스도 독립적인 보관·조회 및 운영 정책을 가지므로 각각 별도 패키지를 사용한다. 최상위 `persistence.repository` 공통 패키지는 생성하지 않는다.

## 5. 영속성 구현계획

### 5.1 CustomerRepository

- `JpaRepository<Customer, Long>`를 확장한다.
- `Optional<Customer> findByCustomerId(String customerId)`와 `boolean existsByCustomerId(String customerId)`를 제공한다.
- 고객 생성 전 존재 여부 확인과 FK 대상 검증에 사용한다.

### 5.2 WalletRepository

- 일반 조회용 `findByCustomerId`와 잔액 변경용 `findByCustomerIdWithLock`을 분리한다.
- 잠금 조회는 `@Lock(LockModeType.PESSIMISTIC_WRITE)`와 명시적 JPQL을 사용한다.
- `jakarta.persistence.lock.timeout=3000` Query Hint를 적용한다.
- 잠금 메서드는 Application 트랜잭션 안에서만 호출한다.

### 5.3 WalletTransactionRepository

- `JpaRepository<WalletTransaction, Long>`를 확장한다.
- 충전 멱등 재조회용 `findByIdempotencyKey`를 제공한다.
- 운영 추적용 `findAllByPaymentIdOrderByCreatedAtAsc`를 제공하되 상세 조회 조립은 Application Query 단계에서 수행한다.

### 5.4 PaymentRepository

- 멱등 재조회용 `findByIdempotencyKey`를 제공한다.
- 고객 소유권 검증용 `findByIdAndCustomerId`를 제공한다.
- 동일 결제의 동시 부분 취소를 직렬화하기 위해 `findByIdWithLock`에 `PESSIMISTIC_WRITE`와 3초 타임아웃을 적용한다.
- 고객 목록 조회는 `findAllByCustomerId(..., Pageable)`로 제공한다.
- 운영자 다이나믹 검색은 후속 Query 레이어에서 `JpaSpecificationExecutor<Payment>`를 사용하도록 확장 지점만 준비한다.

### 5.5 PaymentCancelRepository

- 취소 멱등 재조회용 `findByIdempotencyKey`를 제공한다.
- 원 결제 이력 조회용 `findAllByPaymentIdOrderByCreatedAtAsc`를 제공한다.
- 원 결제 잠금을 먼저 획득한 뒤 취소 레코드를 생성하는 잠금 순서를 문서화하여 교착 위험을 줄인다.

### 5.6 PgResponseLogRepository

- 결제별 PG 응답 메타데이터 조회를 제공한다.
- 평문 응답을 받거나 자동 복호화하지 않고 암호문 엔티티만 저장한다.
- 암호문 전체가 일반 `toString` 또는 로그에 포함되지 않도록 한다.

### 5.7 PaymentOutboxRepository

- `INIT` 상태이면서 기준 시각 이전에 생성된 이벤트를 오래된 순서로 제한 조회한다.
- 복수 스케줄러 확장을 고려해 후보 조회와 개별 잠금 조회를 분리한다.
- `findByIdWithLock`은 `PESSIMISTIC_WRITE`를 사용하며 처리 후 `PUBLISHED` 또는 재시도 정보를 같은 트랜잭션에서 반영한다.
- 1페이즈 H2에서는 단일 스케줄러 실행을 기본으로 하고, 운영 DB 전환 시 `SKIP LOCKED` 지원 여부를 재검토한다.

## 6. 글로벌 멱등성 저장소

### 6.1 도입 배경

현재 `payment`, `payment_cancel`, `wallet_transaction`의 UNIQUE 제약은 테이블 내부에서만 유효하다. 요구사항의 “시스템 전체에서 유일한 `Idempotency-Key`”를 원자적으로 보장하려면 공통 저장소가 필요하다.

### 6.2 V3 Flyway 스키마

`idempotency_record` 테이블을 다음 컬럼으로 생성한다.

| 컬럼 | 용도 |
| --- | --- |
| `idempotency_key` | 전역 기본키 및 클라이언트 멱등키 |
| `request_type` | `PAYMENT`, `PAYMENT_CANCEL`, `WALLET_TOP_UP` |
| `request_fingerprint` | 업무 식별자·고객·금액·유형을 정규화한 요청 지문 |
| `resource_id` | 생성된 결제·취소·거래 식별자, 최초 선점 시 null 허용 |
| `created_at`, `updated_at` | 선점 및 결과 연결 시각 |

- Application 트랜잭션 시작 시 레코드를 먼저 INSERT하여 키를 선점한다.
- UNIQUE 충돌 시 기존 레코드를 조회하고 `request_type`과 `request_fingerprint`를 비교한다.
- 동일 요청이면 연결된 기존 결과를 반환하고 다른 요청이면 `IDEMPOTENCY_CONFLICT`로 변환한다.
- 지문 생성 규칙은 Application 레이어에서 결정하며 평문 개인정보 또는 PG payload를 포함하지 않는다.

## 7. 가상 PG Client 구현계획

### 7.1 계약

- `PgClient`는 `approve(PgApprovalRequest)`와 `cancel(PgCancelRequest)`를 제공한다.
- 요청에는 내부 결제 ID, 멱등키, 고객 ID, 금액, 시나리오가 포함된다.
- 응답에는 결과 상태, PG 거래 ID, 응답 코드 및 암호화 전 원문 payload가 포함된다.
- PG 계약 객체는 Lombok `@Getter`, `@Builder`를 사용하고 변경 불가능하게 구성한다.

### 7.2 결정적 시나리오

| `PgScenario` | 동작 | Application 매핑 예정 |
| --- | --- | --- |
| `APPROVED` | 승인 응답 및 고유 PG 거래 ID 반환 | 결제·취소 후속 처리 |
| `REJECTED` | 거절 응답 반환 | `EXTERNAL_PAYMENT_REJECTED` |
| `ERROR` | `PgClientException` 발생 | `SYSTEM_ERROR` |
| `TIMEOUT` | 타임아웃 분류 예외 발생 | `SYSTEM_ERROR` |

- 기본 시나리오는 `APPROVED`로 하며 테스트 또는 개발 전용 입력으로만 다른 시나리오를 선택한다.
- 실제 장시간 `Thread.sleep`으로 타임아웃을 재현하지 않고 즉시 분류 가능한 예외를 발생시켜 테스트를 결정적으로 유지한다.
- 동일 멱등키의 승인·취소 요청은 결정적인 PG 거래 ID를 생성하여 재현성을 확보한다.
- 응답 원문은 JSON 문자열로 만들되 일반 로그에는 출력하지 않는다.

## 8. AES-256-GCM 암호화 구현계획

### 8.1 설정

- `PaymentSecurityProperties`를 `payment.security` prefix로 바인딩한다.
- 키는 Base64로 인코딩된 정확히 32바이트 AES 키만 허용한다.
- `application.yml`은 `PAYMENT_ENCRYPTION_SECRET` 환경 변수 주입을 사용하고 운영 키 기본값을 소스에 두지 않는다.
- 테스트 전용 키는 `src/test/resources/application-test.yml`에만 둔다.

### 8.2 암호문 포맷

- 알고리즘: `AES/GCM/NoPadding`
- IV: 암호화마다 `SecureRandom`으로 생성한 12바이트
- 인증 태그: 128비트
- 저장 문자열: `v1:{Base64(IV)}:{Base64(ciphertext+tag)}`
- 버전 prefix를 두어 향후 키 회전이나 포맷 변경을 구분한다.

### 8.3 오류와 보안

- 빈 평문, 잘못된 키 길이, 미지원 버전, 손상된 암호문 및 인증 태그 실패를 `EncryptionException`으로 분류한다.
- 예외 메시지와 로그에는 키, 평문, 암호문 전체를 포함하지 않는다.
- 같은 평문을 반복 암호화해도 IV가 달라 서로 다른 암호문이 생성되어야 한다.

## 9. 아웃박스 복구 기반 구현계획

- `OutboxProperties`에 활성화 여부, fixed delay, 고립 판단 시간, batch size, 최대 재시도 횟수를 정의한다.
- `OutboxScheduler`는 `@ConditionalOnProperty`로 기본 비활성화하고 Application의 `OutboxRecoveryPort` 구현이 준비된 경우에만 활성화한다.
- 스케줄러는 후보 ID만 조회하고 각 이벤트 처리는 별도 트랜잭션 경계를 가질 수 있도록 포트에 한 건씩 전달한다.
- 한 이벤트 실패가 배치 전체를 중단하지 않도록 개별 오류를 격리하되 payload와 암호화 정보는 로그에 남기지 않는다.
- 재시도 한도 초과 시 `FAILED`, 성공 시 `PUBLISHED` 상태 전환은 기존 `PaymentOutbox` 도메인 메서드를 사용한다.
- `@TransactionalEventListener(AFTER_COMMIT)`와 실제 PG 승인 처리 연결은 Application 레이어 구현계획에서 구체화한다.

## 10. 설정 변경

`application.yml`에 다음 설정 구조를 추가·정리한다.

```yaml
payment:
  security:
    encryption-key: ${PAYMENT_ENCRYPTION_SECRET:}
  pg:
    default-scenario: APPROVED
  outbox:
    enabled: false
    fixed-delay: 60000
    orphan-threshold: 60000
    batch-size: 50
    max-retry-count: 5
```

- 암호화 빈 기본값은 암호화 Bean 생성 시 명확한 설정 오류를 발생시킨다.
- 로컬 실행 편의를 위한 개발 키 제공 방식은 운영 키와 분리해 후속 실행 프로파일에서 결정한다.
- 설정 클래스에는 `@ConfigurationProperties`를 사용하고 임의의 문자열 `@Value` 주입을 분산시키지 않는다.

## 11. 테스트 계획

### 11.1 Repository 통합 테스트

- 각 Repository의 저장·조회 및 enum 문자열 매핑
- 고객 ID와 업무별 멱등키 UNIQUE 제약
- 글로벌 멱등키 동시 INSERT 시 하나만 성공하는지 검증
- 동일 지갑에 대한 두 트랜잭션의 `PESSIMISTIC_WRITE` 직렬화와 3초 타임아웃 검증
- 동일 결제에 대한 동시 부분 취소 준비 조회의 직렬화 검증
- 아웃박스 기준 시각·상태·정렬·batch size 조회와 개별 잠금 검증

### 11.2 FakePgClient 단위 테스트

- 승인·거절·오류·타임아웃 네 시나리오
- 결제 승인과 취소 응답 계약

## 13. 완료 기준

- 모든 Repository가 현재 Flyway 스키마와 일치하며 애플리케이션 컨텍스트가 기동한다.
- 지갑과 원 결제의 잠금 조회가 동시성 테스트로 검증된다.
- 글로벌 멱등키가 업무 테이블을 넘어 DB에서 원자적으로 유일하다.
- 가상 PG의 네 결과가 외부 환경 없이 결정적으로 재현된다.
- PG 원문이 AES-256-GCM으로 암·복호화되고 변조가 탐지된다.
- 아웃박스 스케줄러가 Application 처리 구현 전 기본 비활성화 상태로 안전하게 구성된다.
- 전체 테스트와 JaCoCo 리포트 생성이 성공한다.
- 전체 시스템 부하 테스트는 수행하지 않고 최종 개발 완료 단계의 별도 계획으로 이관되어 있다.
- 구현과 승인된 계획의 차이가 문서화된다.
- 커밋·푸시·PR은 별도 사용자 요청 전까지 수행하지 않는다.

## 15. 구현 결과

- 사용자 승인 후 merge commit `9f3ee60` 기반의 `feature/infrastructure-layer` 브랜치에서 구현했다.
- Repository를 고객·지갑·결제·취소·PG 로그·아웃박스·멱등성 도메인별 패키지로 분리했다.
- V3 `idempotency_record` 스키마와 동시 선점 검증을 통해 글로벌 멱등키 유일성을 구현했다.
- 지갑 및 원 결제의 3초 타임아웃 비관적 쓰기 잠금과 실제 트랜잭션 대기 테스트를 구현했다.
- 결정적 가상 PG의 승인·거절·오류·타임아웃 및 결제 취소 응답을 구현했다.
- `v1:{IV}:{ciphertext+tag}` 포맷의 AES-256-GCM 암복호화와 변조 탐지 테스트를 구현했다.
- Application 복구 처리기 준비 전 기본 비활성화되는 아웃박스 스케줄러 기반을 구현했다.

- 커밋·푸시·PR은 수행하지 않았다.

## 14. 승인 시 함께 확정할 사항

1. 요구사항 그대로 시스템 전체 멱등키 유일성을 보장하기 위해 V3 `idempotency_record` 테이블을 도입한다.
2. 동일 결제 동시 취소 방지를 위해 `PaymentRepository.findByIdWithLock`에 비관적 쓰기 잠금을 적용한다.
3. AES 키 설정은 Base64 인코딩된 32바이트 키만 허용하고 현재 소스의 평문 기본 키는 제거한다.
4. 아웃박스 스케줄러는 Application 복구 처리기가 구현될 때까지 기본 비활성화한다.
