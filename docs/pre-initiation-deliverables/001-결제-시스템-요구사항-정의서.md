## 2. 프로젝트 배경과 목표

가상의 외부 결제 사업자 API와 연동하는 백엔드 결제 시스템을 구축한다. 고객의 결제 요청을 추적 가능한 원장으로 관리하고, 외부 승인 결과와 고객 지갑 잔액을 반영하며, 고객 문의 및 운영 모니터링에 필요한 결제 이력을 제공하는 것이 목표다.

### 2.1 성공 기준

- 모든 결제 요청은 처리 결과와 관계없이 원장에서 추적할 수 있다.
- 정상 승인된 결제는 지갑 잔액과 결제 상태가 함께 정합성을 유지한다.
- 잔액 부족과 시스템 장애는 구분 가능한 실패 사유로 기록된다.
- 고객 또는 운영자가 API를 통해 결제 이력과 처리 사유를 조회할 수 있다.
- 핵심 비즈니스 시나리오와 예외 시나리오가 자동화 테스트로 검증된다.

## 4. 제품 범위

### 4.1 포함 범위

- 결제 요청 접수 및 결제 원장 생성
- 가상 외부 결제 API 연동
- 고객 지갑 잔액 조회, 충전 및 차감
- 결제 취소, 전액 환불 및 부분 취소(부분 환불)
- 결제 상태와 실패 사유 저장
- 고객·운영자용 결제 이력 조회 API
- 공통 성공·오류 응답 형식
- Swagger/OpenAPI 기반 API 명세 자동 생성 및 Swagger UI 제공
- 대규모 트래픽 대비 부하·경합·장애 내성 테스트와 결과 보고서
- 프로젝트 개발 완료 후 사용자 직접 검증용 테스트 케이스 및 실행 안내서
- H2 기반 데이터 영속화와 핵심 시나리오 테스트

### 4.2 1페이즈 제외 범위

- 실제 PG사 및 금융망 연동
- 운영 환경 배포, 고가용성, 대규모 트래픽 대응
- 인증·인가 및 사용자 개인정보 관리
- 외부 알림, 관리자 화면, 대시보드 UI

인증·인가는 프로젝트 범위에서 제외한다. 그 밖의 제외된 기능성 요구사항은 2페이즈부터 검토하며, 실제 PG 연동과 운영 인프라 범위는 별도 프로젝트 여건에 따라 결정한다. 인증 없이 요청의 `customerId`를 고객 식별자로 사용한다.

## 5. 핵심 업무 흐름

1. 클라이언트가 고객과 결제 금액을 식별할 수 있는 결제 요청을 보낸다.
2. 백엔드는 결제 원장을 `PENDING` 상태로 먼저 저장한다.
3. 백엔드는 외부 결제 API에 승인을 요청하고 `APPROVED`, `FAILED`, `ERROR` 중 하나의 결과를 받는다.
4. 외부 승인이 성공하면 고객 지갑 잔액을 확인한다.
5. 잔액이 충분하면 지갑 금액 차감과 결제 원장의 `COMPLETED` 전환을 하나의 트랜잭션으로 처리한다.
6. 잔액이 부족하면 지갑을 변경하지 않고 결제를 `FAILED` 및 `INSUFFICIENT_BALANCE` 사유로 기록한다.
7. 외부 API 오류·타임아웃 또는 내부 시스템 장애가 발생하면 결제를 `FAILED` 및 `SYSTEM_ERROR` 사유로 기록한다.
8. 처리 결과를 공통 응답 형식으로 반환하고 이후 이력 조회가 가능해야 한다.

## 7. 데이터 및 상태 요구사항

### 7.1 결제 원장 최소 정보

- 결제 식별자, 전역 유일 멱등키, 고객 식별자, 요청 금액
- 현재 상태와 실패 사유
- 외부 결제 요청·응답을 추적할 수 있는 식별 정보
- 생성 시각과 최종 변경 시각

### 7.2 상태 및 사유

| 내부 상태 | 의미 | 대표 사유 |
| --- | --- | --- |
| `PENDING` | 요청을 접수하고 처리가 끝나지 않음 | 없음 |
| `COMPLETED` | 외부 승인 및 지갑 차감 완료 | 없음 |
| `PARTIALLY_CANCELED` | 결제 금액 중 일부가 취소되어 잔여 취소 가능 금액이 있음 | 없음 |
| `CANCELED` | 결제 금액 전부가 취소됨 | 없음 |
| `FAILED` | 결제 완료 불가 | `INSUFFICIENT_BALANCE`, `SYSTEM_ERROR`, `EXTERNAL_PAYMENT_REJECTED` |

외부 결제 거절은 별도 상태를 추가하지 않고 `FAILED/EXTERNAL_PAYMENT_REJECTED`로 표현한다. 환불은 독립된 결제 상태가 아니라 전액 또는 부분 취소 성공으로 발생하는 지갑 입금으로 정의한다.

### 7.3 외부 API 응답 로그 최소 정보

- 로그 식별자와 결제 식별자
- 외부 거래 식별자와 외부 응답 코드
- 응답 수신 시각
- 암호화된 외부 응답 원문 전체

검색과 모니터링에 필요한 메타데이터는 별도 컬럼으로 관리한다. 민감정보가 포함될 수 있는 응답 원문은 애플리케이션 수준에서 암호화하고 암호화 키를 소스 코드나 데이터베이스에 함께 저장하지 않는다.

### 7.4 취소 거래 최소 정보

- 취소 식별자와 원 결제 식별자(외래키)
- 취소 요청용 전역 유일 멱등키
- 전액·부분 취소 유형과 요청 금액
- 취소 상태(`PENDING`, `COMPLETED`, `FAILED`)와 실패 사유
- 외부 취소 거래 식별자
- 생성 시각과 완료 시각

원 결제와 취소 거래는 1:N 관계로 관리한다. 원 결제에는 원 결제 금액과 누적 취소 완료 금액을 유지하며, 취소 가능 금액은 두 값의 차이로 계산한다. 지갑 거래 이력에는 원 결제 식별자와 취소 식별자를 함께 기록한다.

### 7.5 지갑 및 지갑 거래 이력 최소 정보

- 지갑 식별자, 전역 유일 고객 식별자, 현재 잔액
- 지갑 생성 시각과 최종 변경 시각
- 지갑 거래 식별자와 거래 유형(`TOP_UP`, `PAYMENT`, `REFUND`)
- 거래 금액과 처리 후 잔액
- 관련 결제 식별자 또는 취소 식별자
- 충전 거래의 전역 유일 멱등키
- 거래 생성 시각

고객당 하나의 지갑만 허용하며 지갑은 명시적으로 생성하고 초기 잔액은 0원으로 설정한다. 시스템은 결제나 충전 요청을 계기로 지갑을 자동 생성하지 않는다.

## 8. 비기능 요구사항과 기술 제약

### 8.1 기술 기준선

| 구분 | 기준 |
| --- | --- |
| 언어 | Java 17 |
| 애플리케이션 프레임워크 | Spring Boot 3.5.16 |
| 빌드 도구 | Gradle 8.14.3 Wrapper |
| 웹/API | `spring-boot-starter-web` |
| 데이터 접근 | Spring Data JPA |
| 입력 검증 | Bean Validation |
| 운영 및 상태 확인 | Spring Boot Actuator |
| 데이터베이스 및 스키마 관리 | H2 Database, Flyway |
| 테스트 및 커버리지 | JUnit 5, JaCoCo HTML/XML Report |
| API 문서화 | Swagger UI / OpenAPI 3 (`springdoc-openapi`) |

Spring Boot는 전체 메이저 버전의 최신 버전이 아니라 프로젝트 조건인 3.x 범위의 최신 안정 버전인 3.5.16을 사용한다. 개발 및 빌드 환경 차이를 줄이기 위해 시스템에 설치된 Gradle이 아닌 프로젝트의 Gradle Wrapper를 기준으로 실행한다.

Swagger/OpenAPI 명세는 Controller와 요청·응답 DTO를 기준으로 생성하며 다음 원칙을 적용한다.

- 모든 공개 API의 목적, 입력값, `Idempotency-Key` 헤더 및 업무 제약을 문서화한다.
- 공통 `ApiResponse<T>` 성공·오류 구조와 주요 HTTP 상태 및 업무 오류 코드를 명시한다.
- 고객용 API와 운영자용 API를 태그로 구분하고 인증·인가가 1페이즈 제외 범위임을 표시한다.
- Swagger UI에서 개발·검증 환경의 API 명세를 조회하고 요청을 실행할 수 있어야 한다.
- Markdown API 명세서는 제품 관점의 계약과 예시를 제공하고, 구현과 동기화되는 OpenAPI 문서를 실행 시점의 상세 명세로 사용한다.

#### Spring Web MVC 선택 근거

본 시스템은 결제, 취소, 지갑 및 이력 조회를 HTTP 요청-응답 방식의 REST API로 제공한다. 
데이터 접근 기술인 Spring Data JPA와 H2 JDBC가 블로킹 방식이므로 동일한 동기 처리 모델인 Spring Web MVC를 적용하면 
트랜잭션 경계와 예외 처리를 일관되게 구성할 수 있다. 또한 `@RestController`, 요청 매핑, JSON 직렬화, Bean Validation 연계 및 공통 오류 응답 처리를 과제 범위에 맞는 낮은 복잡도로 제공한다.
대안인 Spring WebFlux는 비동기·논블로킹 처리에 적합하지만, JPA와 JDBC 호출이 블로킹이므로 이 프로젝트에서 채택하면 논블로킹 처리의 이점은 제한되고 실행 모델과 테스트 복잡도만 증가한다. 
따라서 현재 요구사항과 기술 기준선에서는 Spring Web MVC를 선택한다.

### 8.2 데이터 및 품질 제약

- 데이터베이스는 H2 인메모리 DB를 사용한다.
- 애플리케이션 재시작 시 데이터 소실을 허용하고 실행할 때마다 스키마를 새로 생성한다.
- 샘플 고객·지갑 데이터는 초기화 스크립트로, 테스트 데이터는 독립된 테스트 픽스처로 제공한다.
- H2 파일 모드와 운영용 데이터베이스 마이그레이션은 2페이즈에서 검토한다.
- 잔액 확인, 지갑 차감, 결제 완료 기록은 트랜잭션으로 원자성을 보장한다.
- 금액은 부동소수점 오차가 없는 자료형을 사용하고 음수 및 0원 요청 정책을 검증한다.
- 통화는 원화(`KRW`)만 지원하고 금액은 1원 단위의 양의 정수로 처리한다.
- 별도의 사업상 최소·최대 결제, 충전 및 취소 금액 한도는 두지 않는다.
- 동시 결제에 대한 잔액 정합성 정책을 구현 전에 확정한다.
- 멱등키에는 데이터베이스 유일성 제약을 적용하고 외부 결제 API에도 동일한 키를 전달한다.
- 외부 API 타임아웃을 설정하고 타임아웃 발생 시 `FAILED/SYSTEM_ERROR`로 처리한다.
- 로그에 결제 식별자를 포함하되 민감정보 및 전체 외부 응답을 무분별하게 기록하지 않는다.
- 외부 응답 원문은 일반 애플리케이션 로그에 출력하지 않고 전용 로그 테이블에 암호화하여 저장한다.
- 외부 응답 원문의 암호화 키는 실행 환경에서 주입하고 저장 데이터와 분리해 관리한다.
- 주요 정상·실패·동시성 시나리오는 자동화 테스트로 검증한다.
- Gradle 테스트 완료 후 JaCoCo 커버리지 HTML 리포트를 자동 생성하여 협업자가 브라우저에서 패키지·클래스·라인별 테스트 범위를 확인할 수 있어야 한다.
- CI 연계와 품질 임계치 실패 정책은 2페이즈에서 결정하며, 1페이즈에서는 커버리지 수치를 가시화하고 미검증 영역을 식별하는 데 사용한다.

### 8.3 부하 및 성능 검증 요구사항

부하 테스트는 도메인, 인프라스트럭처, Application, Presentation 및 API 문서화를 포함한 모든 개발사항이 완료되고 기능·통합·인수 테스트가 통과한 후 최종 시스템 검증 단계에서 수행한다. 개발 중인 일부 계층이나 미완성 API를 대상으로 공식 부하 테스트 결과를 산출하지 않는다. 테스트 도구는 최종 검증 구현계획에서 확정하되 스크립트, 입력 데이터 및 실행 방법이 저장소에서 재현 가능해야 한다.

#### 실행 선행 조건

- 전체 Must 기능 요구사항의 구현이 완료되어야 한다.
- Flyway 스키마, 전체 API, 외부 PG 시뮬레이션 및 아웃박스 복구 흐름이 연결되어야 한다.
- 단위·Repository·통합·인수 테스트와 JaCoCo 리포트 생성이 성공해야 한다.
- Swagger/OpenAPI 명세와 실제 API 계약이 일치해야 한다.
- 부하 테스트용 독립 데이터 초기화 및 사후 정합성 검증 절차가 준비되어야 한다.

#### 필수 시나리오

| 시나리오 | 목적 | 검증 항목 |
| --- | --- | --- |
| 일반 지속 부하 | 평상시 혼합 트래픽의 기준 성능 측정 | TPS, p50·p95·p99, 오류율, DB 커넥션 사용량 |
| 순간 급증(Spike) | 짧은 시간에 요청이 급증한 뒤 회복되는지 확인 | 타임아웃·5xx 증가, 회복 시간, 요청 적체 |
| 동일 지갑 집중 경합 | 비관적 잠금 환경에서 초과 차감과 음수 잔액 방지 | 성공·잔액 부족·락 타임아웃 비율, 최종 잔액 정합성 |
| 외부 PG 지연·타임아웃 | 외부 호출 중 DB 커넥션과 잠금이 장시간 점유되지 않는지 확인 | 커넥션 풀 고갈 여부, 원장 상태, 다른 API 영향 |
| 조회 집중 부하 | 고객·운영자 페이징 조회의 정렬·필터 성능 확인 | 응답시간, TPS, 쿼리 및 인덱스 병목 |

#### 1페이즈 기준 부하 프로파일

- 워밍업 2분 후 최소 10분 동안 100개의 동시 가상 사용자를 유지하는 지속 부하를 기본 프로파일로 한다.
- 순간 급증은 30초 이내에 100명에서 500명의 동시 가상 사용자로 증가시킨 뒤 정상 부하로 복귀시킨다.
- 동일 지갑 경합은 하나의 충분한 초기 잔액을 가진 지갑에 최소 100개의 동시 결제 요청을 발생시킨다.
- 테스트 데이터와 멱등키는 실행마다 충돌 없이 재생성하며, 의도된 잔액 부족·PG 거절 등 업무 실패는 시스템 오류율과 구분한다.
- 테스트 종료 후 결제 원장, 지갑 잔액, 지갑 거래 이력 및 취소 누적 금액의 정합성을 별도로 검증한다.

#### 측정 및 판정 원칙

- 전체 요청의 TPS, p50·p95·p99 응답시간, HTTP 상태별 건수, 시스템 오류율, 락 타임아웃 및 DB 커넥션 풀 지표를 수집한다.
- 시스템 오류율은 의도된 4xx 업무 오류를 제외하고 5xx, 네트워크 오류 및 예상하지 못한 타임아웃을 기준으로 계산한다.
- 1페이즈 단일 애플리케이션·H2 환경의 최초 결과를 회귀 비교 기준선으로 보관한다.
- 1페이즈 판정 기준은 시스템 오류율 1% 미만, 데이터 정합성 위반 0건, 부하 종료 후 애플리케이션 정상 회복이다.
- 응답시간과 TPS의 절대 합격 기준은 실행 장비 영향을 크게 받으므로 최초 기준선 수립 후 동일 환경 회귀 테스트에서 20%를 초과해 악화되면 원인을 분석한다.
- H2 기반 결과를 운영 용량 또는 실제 PG 연동 성능의 보장으로 해석하지 않는다. 운영 DB, 배포 토폴로지 및 실제 네트워크를 반영한 용량 산정은 2페이즈에서 별도로 수행한다.

#### 결과 산출물

- 실행 일시, 커밋 SHA, 애플리케이션·JVM·DB·장비 사양 및 부하 도구 버전
- 시나리오별 부하 프로파일과 사용 데이터
- TPS, 응답시간 백분위, 오류율, 락 및 커넥션 풀 지표
- 데이터 정합성 사후 검증 결과
- 발견된 병목, 재현 절차, 개선 권고 및 직전 기준선 대비 변화

### 8.4 사용자 직접 테스트 문서 요구사항

사용자 직접 테스트 케이스와 실행 안내서는 개발 중간 단계에 작성하지 않는다. 도메인, 인프라스트럭처, Application, Presentation, Swagger/OpenAPI 및 모든 Must 기능 구현이 완료되고 내부 단위·통합·인수·부하 테스트 결과가 확정된 후 최종 인수·인계 단계에서 실제 완성된 API와 실행 환경을 기준으로 작성한다.

#### 작성 선행 조건

- 모든 개발사항과 Flyway 마이그레이션이 완료되어야 한다.
- 전체 자동화 테스트와 JaCoCo 리포트 생성이 성공해야 한다.
- 최종 부하 테스트와 데이터 정합성 검증이 완료되어야 한다.
- Swagger/OpenAPI 명세와 실제 요청·응답 및 오류 코드가 일치해야 한다.
- 사용자 테스트에 사용할 실행 명령, 환경 변수, 샘플 데이터 및 초기화 절차가 확정되어야 한다.

#### 테스트 케이스 필수 범위

- 애플리케이션 기동, 상태 확인 및 H2 초기 데이터 확인
- 고객 지갑 생성, 중복 생성, 잔액 조회 및 멱등 충전
- 정상 결제, 잔액 부족, PG 거절, PG 오류 및 타임아웃
- 동일 결제 요청 재전송과 다른 요청의 멱등키 충돌
- 전액 취소, 부분 취소, 반복 부분 취소, 취소 한도 초과 및 취소 멱등성
- 고객용 결제 이력과 운영자용 조건·페이징 조회
- 외부 PG 응답 암호화 저장 및 민감정보 비노출 확인
- 아웃박스 고립 이벤트 복구와 최종 상태 확인
- 동시 결제·취소 후 지갑, 결제 원장 및 거래 이력 정합성 확인

#### 개별 케이스 작성 형식

각 테스트 케이스는 다음 정보를 포함한다.

| 항목 | 내용 |
| --- | --- |
| 케이스 ID·제목 | 추적 가능한 고유 ID와 검증 목적 |
| 관련 요구사항 | PAY, CAN, WAL, HIS, OPS, EXT, API 요구사항 ID |
| 사전 조건 | 실행 프로파일, 환경 변수, 고객·지갑·결제 데이터 상태 |
| 실행 절차 | 사용자가 순서대로 실행할 명령 또는 Swagger UI 조작 방법 |
| 입력 데이터 | Header, Path, Query, Request Body 및 멱등키 |
| 예상 결과 | HTTP 상태, 공통 응답 코드·메시지·본문 및 상태 전이 |
| 정합성 확인 | H2 조회 방법과 확인할 원장·잔액·거래 이력 |
| 초기화 방법 | 케이스 재실행을 위한 데이터 초기화 또는 신규 식별자 생성 방법 |
| 실제 결과·판정 | 실행 일시, 실제 결과, PASS/FAIL 및 비고 기록란 |

#### 실행 안내서 필수 내용

- JDK와 실행 도구 등 사전 준비 사항
- 필수 환경 변수 설정과 민감정보 취급 주의사항
- Gradle 빌드 및 애플리케이션 실행 명령
- Swagger UI 또는 명령줄 HTTP Client를 이용한 테스트 방법
- H2 Console 접속 및 데이터 정합성 확인 방법
- 테스트 데이터 초기화와 반복 실행 방법
- 오류 발생 시 애플리케이션 로그·원장 식별자를 이용한 확인 방법
- 사용자 발견 결함의 재현 절차와 결과 제출 양식

최종 문서는 `docs/completion-deliverables/`에 완료 산출물로 작성한다. 구현 중인 API를 기준으로 임시 사용자 테스트 문서를 만들지 않으며, 최종 시스템과 문서의 불일치를 방지하기 위해 프로젝트 완료 시점의 커밋 SHA와 Swagger/OpenAPI 명세를 기준으로 검토한다.

## 9. 공통 API 응답 원칙

성공 응답의 기준 구조는 다음과 같다.

```json
{
  "code": "OK",
  "message": "정상적으로 처리되었습니다.",
  "returnObject": {}
}
```

오류 응답도 같은 최상위 구조를 사용하되 HTTP 상태 코드, 업무 오류 코드, 메시지 및 상세 정보 노출 범위를 별도로 정의한다.

### 9.1 조회 API 원칙

- 고객용과 운영자용 조회 API를 논리적으로 분리한다.
- 인증·인가는 범위에서 제외하므로 역할 구분은 API 경로와 응답 정보 수준에 적용한다.
- 고객용 조회는 `customerId`와 결제 소유 고객의 일치를 검증한다.
- 고객용 응답에는 외부 응답 원문과 내부 운영정보를 포함하지 않는다.
- 운영자용 검색 조건은 결제 ID, 고객 ID, 상태, 실패 사유 및 생성일 범위를 지원한다.
- 페이지 번호는 1부터 시작하며 기본 페이지 크기는 20건, 최대 크기는 100건이다.
- 기본 정렬은 생성 시각 내림차순이며 목록 응답에 전체 건수와 전체 페이지 수를 포함한다.

## 10. 핵심 인수 시나리오

| 시나리오 | 사전 조건 | 기대 결과 |
| --- | --- | --- |
| 정상 결제 | 외부 승인 성공, 지갑 잔액 충분 | 지갑 차감, `COMPLETED`, 성공 응답 |
| 잔액 부족 | 외부 승인 성공, 지갑 잔액 부족 | 잔액 불변, `FAILED/INSUFFICIENT_BALANCE`, 오류 응답 |
| 외부 API 거절 | 외부 승인 거절 | 잔액 불변, 합의된 실패 상태·사유 저장 |
| 외부 API 장애 | 타임아웃 또는 오류 | 잔액 불변, `FAILED/SYSTEM_ERROR`, 추적 정보 저장 |
| 내부 처리 장애 | 잔액 차감 또는 원장 갱신 실패 | 부분 반영 없이 롤백, 추적 가능한 오류 처리 |
| 동시 결제 | 동일 지갑에 복수 요청 | 초과 차감 및 음수 잔액 방지 |
| 중복 요청 | 동일 요청 재전송 | 합의된 멱등성 정책에 따라 중복 결제 방지 |
| 전액 취소 | 완료된 결제의 남은 금액 전액 취소 | 외부 취소, 지갑 전액 환불, 취소 거래 `COMPLETED`, 원 결제 `CANCELED` |
| 부분 취소 | 완료된 결제의 일부 금액 취소 | 외부 부분 취소, 해당 금액 환불, 원 결제 `PARTIALLY_CANCELED` |
| 반복 부분 취소 | 동일 결제에 여러 부분 취소 | 누적 취소 금액이 원 결제 금액을 초과하지 않음 |
| 취소 실패 | 외부 취소 거절 또는 오류 | 원 결제 상태 불변, 취소 거래에 실패 상태와 사유 기록 |
| 일반 지속 부하 | API 구현 완료, 테스트 데이터 준비 | 100 동시 사용자로 10분 수행 후 시스템 오류율 1% 미만, 정합성 위반 0건, 결과 보고서 생성 |
| 순간 급증 | 정상 부하 상태 | 최대 500 동시 사용자 급증 후 애플리케이션이 정상 부하 처리 상태로 회복 |
| 동일 지갑 집중 경합 | 충분한 잔액을 가진 동일 지갑 | 초과 차감·음수 잔액·중복 거래 없이 최종 잔액과 거래 이력이 일치 |
| 외부 PG 지연 부하 | 지연·타임아웃 시나리오 활성화 | DB 커넥션 풀 고갈 없이 다른 API가 처리되고 실패 원장이 추적 가능 |

## 11. 확정된 의사결정

- 인증·인가는 범위에서 제외하고 `customerId`로 고객을 식별한다.
- 취소, 전액 환불 및 부분 취소는 1페이즈 범위에 포함한다.
- 그 밖의 제외된 기능성 요구사항은 2페이즈부터 검토한다.
- 결제 원장은 최초 `PENDING`으로 저장하고 외부 승인 성공 후 지갑 잔액을 확인한다.
- 잔액이 충분하면 지갑 차감과 `COMPLETED` 전환을 하나의 트랜잭션으로 처리한다.
- 외부 API 오류·타임아웃 또는 내부 시스템 장애는 `FAILED/SYSTEM_ERROR`로 처리한다.
- `Idempotency-Key`는 시스템 전체에서 유일하며 외부 결제 API에도 동일한 값을 전달한다.
- 같은 멱등키와 같은 요청은 기존 결과를 반환하고, 고객 또는 금액이 다른 요청은 `409 Conflict`로 거절한다.
- 외부 `FAILED`는 `FAILED/EXTERNAL_PAYMENT_REJECTED`, 외부 `ERROR`와 타임아웃은 `FAILED/SYSTEM_ERROR`로 매핑한다.
- 외부 응답 원문 전체는 결제별 전용 로그 테이블에 암호화해 저장하며 암호화 키는 저장 데이터와 분리한다.
- 원 결제와 취소 거래는 1:N으로 연결하며 전액·부분 취소 성공이 고객 지갑 환불을 발생시킨다.
- 원 결제는 누적 취소 금액에 따라 `PARTIALLY_CANCELED` 또는 `CANCELED`로 전환한다.
- 취소 요청은 별도 멱등키를 사용하며 취소 실패는 원 결제가 아닌 취소 거래에 기록한다.
- 통화는 원화(`KRW`)로 한정하고 금액은 1원 단위의 양의 정수로 처리하되 별도 최소·최대 한도는 두지 않는다.
- 고객당 하나의 지갑을 명시적으로 생성하며 초기 잔액은 0원으로 설정한다.
- 지갑 충전에는 별도 멱등키를 적용하고, 외부 직접 차감·환불 API는 제공하지 않는다.
- 결제 차감과 취소 환불을 포함한 모든 잔액 변경은 지갑 거래 이력으로 저장한다.
- 고객용과 운영자용 조회 API는 논리적으로 분리하며 운영자용 API에서 상세 모니터링 정보를 제공한다.
- Swagger/OpenAPI를 이용해 요청·응답 모델과 오류 정책을 문서화하고 Swagger UI를 제공한다.
- 반복 가능한 부하 테스트로 일반 부하, 순간 급증, 동일 지갑 경합, 조회 집중 및 외부 PG 지연 상황의 기준 성능과 정합성을 검증한다.
- 부하 테스트는 모든 개발사항과 선행 자동화 테스트가 완료된 후 최종 시스템 검증 단계에서 수행한다.
- 사용자 직접 테스트 케이스와 실행 안내서는 모든 개발 및 내부 검증이 완료된 후 최종 인수·인계 산출물로 작성한다.
- 목록 조회는 1페이지부터 시작하고 기본 20건·최대 100건, 생성 시각 내림차순으로 제공한다.
- H2는 인메모리 모드로 사용하고 재시작 시 데이터 소실을 허용하며 실행할 때마다 스키마를 재생성한다.
- 샘플 데이터는 초기화 스크립트 또는 테스트 픽스처로 제공하고 파일 모드와 운영용 마이그레이션은 2페이즈에서 검토한다.

## 12. 완료 정의

- 본 문서의 Must 요구사항과 주요 정책이 합의되어 있다.
- 승인된 구현 계획과 아키텍처 결정 기록이 존재한다.
- API 명세, 데이터 모델, 상태 전이 및 오류 코드가 문서화되어 있다.
- Swagger UI에서 전체 공개 API의 OpenAPI 명세를 확인하고 개발 환경 API를 호출할 수 있다.
- JaCoCo HTML 리포트가 생성되고 도메인 레이어의 클래스·메서드·라인 커버리지를 확인할 수 있다.
- 합의된 부하 테스트 시나리오가 자동 실행되고 성능 지표, 데이터 정합성 및 병목 분석 결과가 보고서로 남는다.
- 프로젝트 완료 시점의 실제 API를 기준으로 사용자 직접 테스트 케이스와 실행 안내서가 완료 산출물에 포함된다.
- 핵심 인수 시나리오 테스트가 통과한다.
- 구현과 합의된 요구사항 간 차이가 있다면 이유와 영향을 변경 기록에 남긴다.
