# ADR 0003: Outbox-Ready (점진적 아웃박스) 아키텍처 및 마이그레이션 전략

- **상태**: 승인됨 (Accepted)
- **날짜**: 2026-08-08
- **작성자**: Lead System Architect / Tech Lead

---

## 1. 맥락 및 과제 (Context & Challenge)

Spring Event와 `@TransactionalEventListener(phase = AFTER_COMMIT)`를 활용하여 외부 PG 연동 시 DB 커넥션 점유를 해제하였으나, 다음과 같은 엣지 케이스가 존재한다:

* **이벤트 유실 위험 (Event Loss)**: `PENDING` 결제 원장이 DB에 `COMMIT`된 직후외부 PG 호출 직전에 JVM이 비정상 종료(Crash, OOM, SIGKILL)되거나 서버가 재부팅되면 메모리 상의 Spring Event가 유실되어 결제가 `PENDING` 상태로 영구 고립될 가능성이 있다.
* **Phase 2 마이그레이션 리스크**: 1페이즈에서 이벤트 보장 메커니즘을 전무한 상태로 설계했다가 Phase 2에서 Kafka 및 분산 메시징으로 확장할 경우, 핵심 결제 원장 도메인(`PaymentService`)의 스키마와 코드 전체를 대대적으로 수정해야 하는 위험이 존재한다.

---

## 2. 의사결정 (Decision): Outbox-Ready 아키텍처 채택

Phase 1에서 인프라 오버엔지니어링(Kafka/CDC 구축)을 피하면서도 이벤트 유실을 100% 방지하고 Phase 2 리팩토링 리스크를 0(Zero)으로 만드는 **"Outbox-Ready (점진적 아웃박스)"** 아키텍처를 도입한다.

### 2.1 아키텍처 메커니즘

1. **원자적 아웃박스 레코드 생성 (Atomic Write)**:
   * `Payment` PENDING 원장을 저장하는 동일한 DB 트랜잭션 내에서 `payment_outbox` 테이블에 `INIT` 상태의 이벤트를 함께 저장한다.
   * `Payment` 원장 저장과 `PaymentOutbox` 저장이 하나의 트랜잭션으로 원자적(Atomic)으로 커밋된다.
2. **Spring Event 기반 퍼블리싱 & 상태 업데이트**:
   * `AFTER_COMMIT` 시점에 Spring Event가 외부 PG 승인 및 잔액 차감을 호출하고, 정상 완료 시 Outbox 레코드를 `PUBLISHED`로 변경한다.
3. **Outbox Poller 스케줄러 복구 (`OutboxScheduler`)**:
   * 서버 비정상 종료 등으로 1분 이상 `INIT` 상태로 방치된 Outbox 레코드가 있다면, 백그라운드 `OutboxScheduler`가 이를 감지하여 유실된 이벤트를 안전하게 재시도한다.

### 2.2 Phase 2 마이그레이션 이점

* **결제 도메인 리팩토링 Zero**: Phase 2에서 Kafka/RabbitMQ 등 외부 메시지 브로커로 전환할 때, `PaymentService`나 DB 결제 원장 코드/스키마는 단 1줄도 수정할 필요가 없다.
* **이벤트 발행 구현체만 교체 (Swap)**: `OutboxEventListener` 내부의 이벤트 발송 로직만 Spring Event ➡️ `KafkaTemplate`으로 스왑하면 된다.

---

## 3. 결과 및 기대 효과 (Consequences)

* **정합성 완전 보장**: JVM Crash 시에도 DB `payment_outbox` 기록으로 유실된 결제가 100% 복구됨.
* **미래 확장성 보장**: Phase 2 분산 아키텍처 전환 시 마이그레이션 위험도 0%.
* **경량성 유지**: 추가 브로커 설치 없이 H2 DB 테이블 1개와 경량 스케줄러로 목적 달성.
