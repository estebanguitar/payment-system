# ADR-004: 감사 로그 수집 및 저장 전략

## 상태

승인됨 (감사 로그 삭제 기능 제외)

## 배경

`AUD-001`, `AUD-002`는 성공·실패 API 요청 이력의 추적과 민감정보 비수집, 추가 전용 보존을 요구한다. 감사 로그는 업무 트랜잭션이 롤백되더라도 남아야 하며, 감사 저장 장애가 이미 완료된 결제 원장을 되돌려서는 안 된다. 현재 시스템에는 외부 메시지 브로커나 별도 감사 저장소가 없다.

## 결정 제안

- Servlet 처리 전체를 관찰할 수 있는 `OncePerRequestFilter`에서 감사 이벤트를 수집한다.
- 요청 완료 시 업무 트랜잭션과 분리된 `REQUIRES_NEW` 트랜잭션으로 전용 `audit_log` 테이블에 동기 저장한다.
- 인메모리 비동기 큐는 프로세스 종료 시 유실될 수 있으므로 사용하지 않는다.
- 저장 실패는 이미 완료된 업무 결과를 변경하지 않고 payload 없는 비상 로그와 실패 지표로 탐지한다.
- 코드 허용 목록에 포함된 메타데이터만 저장하며 body, 인증정보, 멱등키, 쿼리 문자열 및 개인정보는 저장하지 않는다.
- 인증 체계 도입 전 `X-Client-Id`는 비신뢰 추적 정보로만 취급한다.
- 감사 로그 삭제 API, 자동 삭제 및 보존 만료 삭제는 구현하지 않는다.

## 결과와 트레이드오프

- 업무 성공·실패 및 롤백과 독립된 감사 이력을 남길 수 있다.
- 요청마다 추가 DB 쓰기와 별도 트랜잭션 비용이 발생한다.
- DB 전체 장애에서는 업무 원장과 감사 로그의 동시 완전 보장이 불가능하다.
- 더 강한 전달 보장이 필요하면 외부 durable broker 또는 별도 수집 에이전트가 필요하며, 최종 부하 테스트의 지연·유실 측정 결과를 근거로 후속 ADR에서 결정한다.

## 대안

- Controller AOP: 바인딩 실패와 미매핑 요청을 놓쳐 제외한다.
- 인메모리 비동기 이벤트: 응답 지연은 작지만 프로세스 장애 시 유실되어 제외한다.
- 업무 트랜잭션에 함께 저장: 롤백된 실패 요청이 남지 않아 제외한다.
- 즉시 외부 브로커 도입: 전달 보장은 강화되지만 현재 인프라 범위를 크게 확장하므로 후속 후보로 둔다.
